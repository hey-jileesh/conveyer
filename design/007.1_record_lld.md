### F-2 — `record_key` is a sha256 over the canonical rendering of the declared key-column map; one total pure function; each call site owns its gate — **settled**

In the context of `record_key` composition (007 D-1's registered residue; 006 D-4/D-6's "one shared function, pinned by 007.1's vector file"), facing two call sites with different publication semantics — commit's per-type fact stamping, where every fact must carry a key for dedup/delta identity, and the post_check quarantine writer, where 006 D-6 refuses to publish an identity derived from incomplete key material — **we chose**: `record_key` = **64-lowercase-hex SHA-256 over the canonical-JSON rendering of the map {declared `record_key:` column name → typed value}**, every declared key column always present, rendered by the one canonical grammar already resident in the package (005.1 A-6, `core/canonical.py`) — the `row_hash` idiom applied to a third subject; the derivation is **one plain-value pure function, total over its input domain** (nulls render canonically as values — the function never refuses a complete map), and **the gate is the call site's, never the function's**: commit derives unconditionally; the post_check writer derives iff every declared key column is non-null, else `record_key` stays NULL (006 D-6, cited — not restated); **and rejected** a composite delimited string (delimiter injection breaks injectivity unless a second bespoke escaping grammar is invented and kept aligned across two lanes; unbounded length; and the security argument — a composite string embeds cell values into `record_key`, a column that 005.1 §4.5's remediation queue views project while `row_snapshot` stays classification-restricted, so composition would silently reclassify payload — an argument that stands: embedding raw cell values is *unconditionally* payload, while the hash form's own conditional classification is the [DS-1] rule below), **and rejected** embedding or appending `content_hash` (identity and value are the two *different* axes delta detection compares — "per `record_key`, drop iff `content_hash` unchanged" (D-2) dies if a content change mints a new identity), **and rejected** per-site derivation variants (partial-key hashing at the quarantine site was already rejected by 006 D-6; two implementations is the two-evaluators trap 005.1 A-7 names), **to achieve** a fixed-width, cross-site-identical identity that any interpreter can reproduce from the committed vectors — its classification governed by the conditional rule below, never by a blanket safety claim [DS-1] — with composition changes localized to this doc + its vector files (006.1 cites, never restates), **accepting that** a hash key is opaque — "which policy is this" is a join back through the fact table, not a read of the key — and that when a feed declares `record_key:` = the full declared column set, `record_key` coincides with a same-serializer `content_hash` (subjects identical); the coincidence is benign — delta detection remains correct, every content change is honestly a new identity — and is noted so nobody treats hash-family incomparability as a domain-separation guarantee rather than what it is, a subject-shape property.

**Classification rule [DS-1] (security gate `conveyer-hpp.6`, at +e4 — the *claim* changes, the composition does not):** the earlier blanket "classification-safe" phrasing is withdrawn as unsound for enumerable key material — `record_key` is an **unsalted, deterministic** sha256 over declared key-column values, and carrier key domains (policy/agent/member identifiers, periods, line numbers) are dictionary-enumerable, so the hash is reversible by enumeration and, even unreversed, a **stable cross-table pseudonymous identifier** of the keyed subject. The rule that replaces the claim: **`record_key` inherits pseudonymous/identifying classification whenever any declared `record_key:` column is PII-classified**; queue-view projection of `record_key` (005.1 §4.5's remediation views, 006 D-6's queue grouping, newly populated on post_check quarantine rows by 006.1 §10) is then **governed per-pipeline — a 012-register decision (006.1 §16.7), never a projection-by-default**. The **keyed-derivation alternative** — HMAC with a platform secret, which preserves every F-2 property (fixed width, cross-site identity, vector-pinnable: vectors re-pin under the key) while enabling linkability shredding by secret destruction, where a plain unsalted hash forecloses later keyed tokenization — is registered as an **explicit input to `conveyer-4ot.41`** (§16's row, mirrored in 006.1 §16.9, noted on the bead). Nothing in this paragraph reopens F-2's settled composition, gates, or vectors.

### F-4 — Commit is N guarded appends and fold is N MERGEs; guard grain and the one-commit invariant are per (stage, table); skip decisions are per-table decide-then-do — **settled** (register source: 004.1 errata row 19, `conveyer-3w8` item 1)

In the context of generalizing 004's single-table commit/fold soundness argument to 006 D-4's per-type candidate frames (one fact table and one state table per declared fact type), facing the register 004.1 errata row 19 hands this doc verbatim, **we chose** the table-wise generalization exactly as registered: **commit = N guarded appends**, one per `(batch_id, fact_table)`, iterated in the declared fact-type order (a total, deploy-pinned order — the declaration surface is 006.1 P-1's); **fold = N MERGEs**, one per state table, same iteration order; the **guard grain** and 004.1 I-4's **one-commit invariant** become **per `(stage, table)`** — exactly one snapshot per (stage, table) per batch, N snapshots per stage; the **zero-fact corollary holds per-table** (a type all of whose candidates dropped leaves no guard row for *that* table only); and the **commit skip is per-table decide-then-do** — probe the guard, then append, table by table — **and rejected** a batch-grain skip decision ("any table has facts ⇒ skip all appends" would, after a kill between type appends, silently lose the unwritten tables' facts — the one loss class fail-open cannot absorb; errata row 19 names it), **and rejected** a batch-grain all-tables guard for the demotion doors (an all-tables reading of fact presence would re-render verdicts against re-resolved co-effect snapshots with some facts durably committed — the [H-2] wedge; door semantics are 006.1's, see §7.1), **to achieve** per-table convergence under every partial-kill interleaving with no new machinery — each (stage, table) pair independently carries the same guard/append soundness 004 D-4 argued once — **accepting** N guard probes and N ledger-visible snapshots per stage where there was one (bounded by the declared type count, single-digit in practice), and that the run-ledger/context grain under N tables is a §4 decision this revision defers.

### F-6 — The `ordering:` comparability set is closed: {int, long, decimal(p,s), date, timestamp, string}; comparison semantics pinned per type; everything else is a bind defect — **settled**

In the context of pinning the comparable-type set 006 D-4's bind-time "ordering types comparable" validator cites (seam: 006.1 §5 checks this list, never a second one), facing D-3's total order — field-wise lexicographic over (declared `ordering:` columns, `source_ts`, `content_hash`), strict inequality, null-ranks-lowest [T-11] — which is only as sound as each element type's own order, **we chose** the closed set **{int, long, decimal(p,s), date, timestamp, string}** with the per-type semantics of §8.1 (numeric order for int/long/decimal — scale is *not* order-significant; chronological order for date/timestamp with timestamps compared as UTC instants; **binary UTF-8 byte order** for string — no collation, no unicode normalization, matching the canonical grammar's verbatim stance), **and rejected** bool (no recency meaning, no customer — an `ordering:` bool is almost certainly an authoring error; admitting it later is additive), **and rejected** float/double (outside the canonical value domain entirely — `canonical_json` rejects floats, and D-1 hashes every declared column, so a float column cannot even *be* a fact column in Phase 1; handed to 006.1's fact-schema type grammar as a structural constraint, §8.1), **and rejected** complex types (array/map/struct — Spark can compare some of them, but nested-null semantics and cross-lane rendering are unargued; bind defect now, additive growth with a customer), **to achieve** an ordering struct whose comparison is reasoning-small — every element type has one stated, engine-stable total order, and the two framework-appended elements (`source_ts`: timestamp; `content_hash`: 64-hex string, never null) are themselves in-set, so the whole struct's comparability is closed under this one list — **accepting that** string ordering is codepoint order with its named authoring trap (`"10" < "9"` — 009's authoring guidance carries the warning), and that a feed wanting a bool or complex ordering key waits on an additive grammar release.

### F-8 — The I-24 structural check is retained per-table as the commit-stage backstop; demoted NULL-`domain_id` rows never reach it on evaluated paths; a backstop hit is a defect, never data — **settled**

In the context of I-24's registered question — 007 D-3(d) demoted NULL-`domain_id` from I-24's fail-fast to quarantine via 006 D-6's framework-reserved implicit check, so does the commit-stage check survive? — facing the invariant I-24 exists to protect (a NULL `domain_id` never matches a MERGE `ON` clause, so such a fact is re-INSERTed by every fold rerun — fold has no guard, and rerun-is-a-no-op goes silently false), **we chose**: the structural check **stays at commit, generalized per-table** — before each fact table's append: non-null `domain_id` on every row of that type's admitted frame, plus the pure column-set diff against that table (004.1 I-24's mechanism unchanged) — as the **backstop**, with the routing split stated plainly: *data*-borne nulls are consumed one stage earlier by the implicit `business/missing-domain-id` check (006 D-6: evaluated first, before all authored checks), so what reaches the backstop is never data; **and rejected** deleting the check as redundant with the demotion (the "never reach it" claim is an argument with a boundary, not an identity — see §7.3: on the durable-authority doors under drifted recomputation, an *unevaluated* candidate set can reach a fact table whose guard is absent — and even the guard-present subtraction path can pass a **drift-born** row the original attempt never adjudicated [AE-3] — and only the backstop stands between that and a silent fold-convergence break), **and rejected** widening the backstop into a second business-check surface (it checks exactly the two structural facts the fold's soundness rests on — `domain_id` non-null, schema match — anything more re-creates judgment outside 006 D-1's declared surface), **to achieve** defense in depth with clean semantics at each layer — candidate seam: data routing with attribution; commit: framework invariant, fail-fast, named defect — **accepting** one redundant aggregate + schema diff per (batch, table) on every healthy run, the price of making "no silent convergence break" structural rather than argued-per-path.

## 5. Canonicalization & Identity

### 5.1 `content_hash` — F-1 fragments only (the rest **DEFERRED to conveyer-hpp.13**)

The full F-1 decision — commit-stage UDF packaging, serializer reuse vs. second implementation, all-declared-columns coverage mechanics, the DC-3 in-plan rendering rule as a normative statement with its tying property test, and the fact-hash vector file location — is `conveyer-hpp.13`'s. Three fragments are settled *now* because F-2 strictly requires them:

1. **Subject disjointness by role.** `content_hash` (all declared fact columns — D-1) and `record_key` (declared `record_key:` columns only) share the canonical grammar and differ only in subject. `content_hash` is **never an input to** `record_key`, and `record_key` is never an input to `content_hash` (both are derived stamps, excluded from D-1's hashed object). Identity is the axis delta detection joins on; value is the axis it compares — complecting them kills D-2 (see F-2's rejection).
2. **Timestamp/date key material crosses the Spark→Python boundary as canonical strings.** 005.1 [DC-3]'s hazard (the UDF boundary converts `TimestampType` via the OS-local zone) applies to every hashed business timestamp, `record_key` inputs included. At any Spark call site, timestamp key columns are rendered **in-plan** (`date_format` under the pinned UTC session zone, `CANONICAL_TIMESTAMP_SPARK_PATTERN`) before reaching the derivation; this is hash-transparent because the canonical grammar renders an aware timestamp and its canonical string to the *same* JSON string (pinned by the `edge-values.json` temporal vector). `date` and `Decimal` cross the boundary typed (environment-independent). 006.1 §10 applies this rule at the post_check writer and cites this section; the tying property test at each call site is deferred test-plan ground (F-1 / §13).
3. **The canonical value domain bounds the fact-column type universe.** `canonical_json` rejects floats and D-1 hashes every declared column — therefore float/double cannot be declared fact-column types in Phase 1. Handed to 006.1 P-1's fact-schema type grammar as a structural constraint (cross-cited in F-6).
4. **The framework fact-stamp column set is enumerated now.** *(Additive at v0.1-seams+e1, `conveyer-hpp.11` — 006.1 §5's fact-column reserved-name collision check strictly requires the enumeration before this doc's §6 DDL lands; same admission rule as fragments 1–3.)* Every fact table's framework-stamped columns are exactly **`batch_id`, `delivery_id`, `feed_id`, `received_at`, `source_ts`, `content_hash`, `record_key`** — D-1's hash-excluded stamps plus the two derived identities of §5.1–§5.2 — with the reserved prefix `_conveyer_` covering internal columns; the enumeration lives as one code constant, `spine/core/record.py::FACT_STAMP_COLUMNS`, consumed by 006.1 §5.3's bind check and restated — never re-enumerated — by §6's DDL tables when `conveyer-hpp.13` lands them. A stamp-set change is an edit to this fragment + §6 and flows to the bind check through the constant, never a second list.

### 5.2 F-2 mechanics — the one derivation function and its two gates

**Function (normative):** `spine/core/identity.py::derive_record_key(key_values) -> str`

- **Input domain:** a mapping of *every* declared `record_key:` column name to its typed value — `str | int | Decimal | date | datetime(aware) | bool | None`, or the value's canonical-string pre-rendering (fragment 2 above). All declared key columns present, always; passing a subset or superset is a caller bug (the map's key set is fixed at bind from the declaration).
- **Output:** `sha256(canonical_json(key_values).encode("utf-8")).hexdigest()` — 64 lowercase hex. Implementation-wise this *is* `core.canonical.row_hash` applied to a third subject; it is declared as its own named function because the seam is the name + subject contract, and because 006 D-6's law — **one shared function, two call sites, never a second implementation** — attaches to this name. Plain-value pure, stdlib-only, no Spark, no pydantic: both the commit-side UDF (F-1, deferred) and the post_check shaper (`frames/quarantine.py::shape_post_quarantine`, 006.1 §10) wrap it.
- **Totality:** total over complete maps. `None` renders as canonical `null` — a value, not a refusal. Column *names* participate in identity (the hashed object is the map, not the value tuple): a declared key-column rename changes every `record_key`, which is correct — a rename is a breaking declaration change and, under additive-only evolution, a new table.
- **Declared order is irrelevant:** canonical rendering sorts keys bytewise; reordering `record_key:` in the declaration does not change derived keys (pinned by `basic.json`).

**The two call sites and their gates** (the gate is policy, owned per-site; the function never gates):

| Call site | Gate | Null key material |
|---|---|---|
| commit — per-type fact stamping (§7, F-1's UDF) | none — every committed fact carries `record_key` | renders canonically; sound for dedup/delta because a drop still requires `content_hash` equality over *all* columns (D-2), so a null-key "collision" can only drop a candidate whose full content already exists — fail-open holds |
| post_check quarantine writer (006.1 §10) | derive **iff every declared key column is non-null**, else `record_key` NULL — 006 D-6, cited | never derived — publishing an identity that collides across genuinely distinct identities into the remediation queue is worse than no identity (006 D-6's argument; the divergence from commit's totality is D-6's accepted floor, not an inconsistency) |

On evaluated paths, a null in `domain_id_col` never reaches commit at all (the implicit check quarantines it — §7.3); commit's null-rendering case therefore arises only for nullable non-`domain_id` key columns, where it is value-determined and fail-open as argued above.

**Classification [DS-1]:** the derived column's classification is F-2's conditional rule (§2 — inherited whenever any declared key column is PII-classified; queue-view projection per-pipeline-governed), cited by 006.1 §10 at the quarantine site — not restated here.

**Change discipline (the non-duplication rule, both docs restate it):** composition is normative *here and in the vectors only*. 006.1 §10 cites this section and §5.3, restating nothing but its own gate and the DC-3 obligation at its site. A future composition change edits this doc + `contracts/fixtures/record-key/` and must not require a 006.1 edit.

### 5.3 The vector file this doc owns — `contracts/fixtures/record-key/`

Committed with this revision; **the normative surface for `record_key` derivation** (the prose above describes it; the vectors pin it — on divergence the vectors win and the prose is errata'd). Convention: identical to 005.1 §15.2's tagged-JSON fixture convention — one JSON array per file of `{"value": <tagged input>, "canonical": "<exact canonical string>", "sha256": "<64-hex>"}`; `$decimal`/`$date`/`$timestamp` single-key tag objects author typed inputs; the `sha256` field **is** the `record_key`. Every consumer (spine tests, the event lane if it ever derives keys — 009/Track A governance) writes its **own untagging parser** against these committed files — shared vectors, never shared code (004 D-13; 005.1's `_parse_fixture_value` is a reference implementation to read, not import).

| File | Pins |
|---|---|
| `basic.json` (8) | single-column key (the `domain_id`-alone case); multi-column key authored in non-sorted declared order (bytewise rendering order is what hashes); int vs. string discrimination (`{"line_no": 7}` ≠ `{"line_no": "7"}`); **bool vs. string discrimination** (`{"flag": true}` ≠ `{"flag": "true"}` — bool is in F-2's input domain and its canonical `true`/`false` rendering was previously unpinned) [EM-11]; column names participate (`{"agent_code": "x"}` ≠ `{"agent_id": "x"}`) |
| `null-and-empty.json` (3) | null renders as a value (`{"agent_code": null, …}` — the commit-site totality rule; the quarantine site never derives over it, by gate); null ≠ `""` ≠ `"null"` — three distinct keys |
| `edge-values.json` (14) | the composite-string counterexamples as living vectors — the delimiter-injection pair (`{"k1":"a\|b","k2":"c"}` vs `{"k1":"a","k2":"b\|c"}`) and a JSON-lookalike injection value, all distinct keys (injectivity via JSON structure + escaping, the property a delimited composite loses); astral-plane and U+FFFD strings verbatim; **the NFC/NFD discriminator pair [AE-10]** — `é` as U+00E9 vs U+0065 U+0301, authored with `\uXXXX` escapes so a file-level normalization pass cannot silently merge them: visually identical, byte-distinct, **two distinct keys** — the canonical grammar's verbatim no-normalization stance made visible (a partner toolchain switching normalization forms re-keys a feed: fail-open duplicates plus a stranded state row per affected domain — a designed consequence, now pinned and named for authors); **decimal scale is identity-bearing** (`1.2` ≠ `1.20` as keys — canonical Decimal rendering preserves scale; a feed keying on a decimal column takes scale as part of identity, a declaration-reviewable consequence, named); temporal renderings (date ISO; timestamp offset-input → fixed-width UTC — the DC-3 output side); int64 max, **int64 min, and a plain negative int (sign rendering pinned beside the committed maximum)** [EM-11] |

Generation provenance: computed by the resident serializer itself (`spine.core.canonical`), with the generator first reproducing all 31 committed canonical-json vector entries as its own validation gate; the +e2 additions [EM-11]/[AE-10] were generated the same way, reproducing all 19 previously committed record-key vectors first. CI obligation (deferred §13): `derive_record_key` must reproduce every vector.

**Synthetic-only rule [DS-5] (normative, at +e4):** the provenance rule above constrains the generation *tool*; this rule constrains its *inputs* — vector values must be **fabricated, never derived from partner deliveries or lake contents**. "A real row that failed" is never a test vector: committing real partner/member key material — the values *and* their `record_key` hashes — into a git repository gives it a far broader audience than the lake's IAM posture permits. All 25 committed vectors were verified synthetic at the `conveyer-hpp.6` gate; the rule is a **fixture-review checklist item beside the reproduce-committed-vectors gate**, and its generalization to every tagged-JSON fixture family is proposed as a 005.1 §15.2 convention amendment (§16's row).

**Authoring note (009's register, beside F-6's string-ordering trap) [AE-10]:** byte-distinct but visually identical key material (NFC vs NFD) is **distinct identity by design** — the derivation performs no unicode normalization; a feed whose upstream toolchain changes normalization forms silently re-keys, and the remedy is upstream normalization discipline, never a normalizing derivation.

## 7. Commit — per-type mechanics

### 7.1 F-4 mechanics — N guarded appends, per-(stage, table) grain

Register source: **004.1 errata row 19** (`conveyer-3w8` item 1), consumed verbatim; 006 D-4 is the architecture mandate.

- **Iteration:** commit walks the declared fact-type set in declared order (total, deploy-pinned; the declaration surface is 006.1 P-1's). Per table: **decide-then-do** — `table_has_batch(fact_table_t, batch_id)`; if present, skip *that table* (`facts_appended[t] = 0`, snapshot resolved by stamped summary per I-19); if absent: structural check (§7.3), `delta_filter` for that type (F-5, deferred), exactly one `append`. A batch-grain skip is **forbidden** — after a kill between type appends it would silently lose every unwritten table's facts, the one loss class fail-open cannot absorb (errata row 19's named argument).
- **Guard grain / one-commit invariant:** per `(stage, table)` — each fact table advances by exactly one snapshot per batch (I-4/R-13 extended table-wise); a commit stage of an N-type pipeline produces exactly N snapshots on a healthy fresh run.
- **Zero-fact corollary, per-table:** a type all of whose candidates dropped leaves no guard row *for that table only*; its rerun re-runs the delta filter against a possibly-moved predecessor set — absorbed by fail-open (duplicate facts at worst, correctly ordered), never wrong state (D-2, restated at the new grain).
- **Fold:** N MERGEs, one per state table, same iteration order; fold has no guard by design — convergence per table is the fold contract's (D-3), and 006 D-3's perception-contract clause 2 is **per-table true** (`conveyer-3w8` item 4): a pinned snapshot of any one table never exposes a partial batch of *that* table.
- **The doors, cited forward:** the fact-presence probes at the admission-adjacent writers ([DC-1]/[R2-1]) and the `batch_check` demotion probe evaluate **ANY-table presence** — their *semantics* (why ANY, the [H-2] wedge argument) are **006.1 §8's, normatively**; this doc contributes only the enumeration input (the per-type fact-table set, §4's model ground) and the shared pure planner's probe primitive (`table_has_batch`, composed per table). Do not read door behavior out of this section.
- **Ledger/context accretion grain** under N tables (per-(stage, table) rows vs. per-table maps) is §4's deferred decision; nothing in this section presupposes either.

### 7.3 F-8 mechanics — the I-24 backstop vs. the demoted implicit check

**The check (per-table):** before each fact table's append — (a) `domain_id` non-null on every row of that type's admitted frame; (b) pure column-set diff against that table. Violation = named defect, fail fast, no append, no fold — 004.1 I-24 unchanged in mechanism, applied per table in F-4's loop.

**Why demoted rows never reach it — the argument, path by path** (the demotion: 007 D-3(d) routes data-borne NULL `domain_id` to quarantine via 006 D-6's implicit check, evaluated before all authored checks):

1. **Fresh path:** `admitted = candidates` bag-subtracted against the in-memory violations (006 §5.4 [DC-5]); the implicit check fires on every null-`domain_id` row, so every such row is in the subtrahend. None survive to commit.
2. **Guard-present rerun:** admitted = recomputed candidates anti-joined against the durable `row_hash` set for `(batch_id, "post_check")`. The implicit check is value-determined (null-ness is a function of the row value), so a recomputed null-`domain_id` candidate hashes identically to the durable quarantine row the original attempt wrote, and subtracts. None survive — **under unchanged inputs. The drift qualifier [AE-3]: the anti-join consumes only rows the original attempt adjudicated.** A rerun re-resolves current co-effect snapshots (D-2's rerun bullet), and a drifted co-effect can make `apply` emit a **new** NULL-`domain_id` candidate the original attempt never produced: no durable hash matches it, it survives the subtraction into the admitted frame, and it reaches the backstop through DURABLE_SUBTRACT — a second reaching path beside path 3, with the same closure (named defect, no append; drift or defect, never data). The batch is then deterministically wedged while the drifted co-effect state persists; 006.1 §11 maps the row and its remediation (corrected delivery/supersession, or co-effect correction, then rerun).
3. **The residual — and why the backstop stays:** the durable-authority doors (006.1 §8's ground: quarantine guard absent + facts present ⇒ empty violation set, *no check evaluation*, all recomputed candidates admitted). Construct the reaching path: an N-type batch killed between type appends (table A has facts, table B does not) is rerun under drifted co-effects or a moved deploy pin; the door fires on ANY-table presence, admitting an **unevaluated** candidate set; table B's guard is absent, so its append proceeds — and a drift-born null-`domain_id` row in type B's frame *would commit*, then be re-INSERTed by every subsequent fold of table B, silently and forever. The backstop converts exactly this into a named, deterministic defect.

**Placement statement, in one line:** the candidate-seam implicit check owns *data* (routing, attribution, `business/missing-domain-id`); the commit-stage backstop owns the *invariant* — its firing is never data routing but always a defect (a framework bug, or drift reaching commit through a durable-authority door), and the demotion narrows neither its `domain_id` half nor its schema-diff half. 006.1's failure map cross-cites this section; this doc's full per-type kill matrix is §11's (deferred).
