### F-1 — `content_hash` at commit: one scalar UDF wrapping the resident serializer derives both fact stamps from one pre-rendered input; coverage is all declared columns by construction; pinned by `contracts/fixtures/fact-hash/` — **settled** (mechanics §5.1; vector family §5.4)

### F-2 — `record_key` is a sha256 over the canonical rendering of the declared key-column map; one total pure function; each call site owns its gate — **settled**

In the context of `record_key` composition (007 D-1's registered residue; 006 D-4/D-6's "one shared function, pinned by 007.1's vector file"), facing two call sites with different publication semantics — commit's per-type fact stamping, where every fact must carry a key for dedup/delta identity, and the post_check quarantine writer, where 006 D-6 refuses to publish an identity derived from incomplete key material — **we chose**: `record_key` = **64-lowercase-hex SHA-256 over the canonical-JSON rendering of the map {declared `record_key:` column name → typed value}**, every declared key column always present, rendered by the one canonical grammar already resident in the package (005.1 A-6, `core/canonical.py`) — the `row_hash` idiom applied to a third subject; the derivation is **one plain-value pure function, total over its input domain** (nulls render canonically as values — the function never refuses a complete map), and **the gate is the call site's, never the function's**: commit derives unconditionally; ### 4.3 F-9 mechanics — the marker table's semantics and the [DC-1] discharge

**The seam (L-1, binding).** Batch-truth lives **only** in the marker table (record-side; control may probe it); attempt-truth lives **only** in the run ledger (lossy; control never reads it — 004 §14.7 unchanged). Any value a control decision needs that exists only in the run ledger is a design defect, not a read to authorize.

**Row kinds and grain (L-2, binding).** One append-only row per `(batch_id, stage, table_name)` — the guard-twin row — plus one **commit-completion** row per batch; no maps, no aggregate rows (a maintained map is an UPDATE or a silent window — both disqualified by M-1 at schema grain). **No fact append may precede its marker row** — marker-first (or atomic): a killed attempt's state is marker-without-facts (over-refusal, permitted), never facts-without-marker (invisible to the probe, forbidden); soundness must not depend on a rerun occurring. The `stage` column exists from day one; fold rows are an additive accretion, never a migration — and completion is **stage-scoped by name** (commit-completion now; a fold-completion row, if 008 ever wants one, is a new row kind, never a re-reading of the old word).

**Write mechanics inside F-4's loop (normative).** Per table *t*, in declared order: (1) guard probe `table_has_batch(fact_table_t, batch_id)` — **present** ⇒ ensure-twin (decide-then-do marker write for `(batch_id, 'commit', fact_table_t)`; M-3's guard-idempotent completion of a missing twin) and skip the append; **absent** ⇒ (2) structural check (§7.3); (3) `delta_filter` (§7.2); (4) **iff the novel set is non-empty**: the guard-twin marker row (decide-then-do; the twin is decided *after* the delta so it twins an actual, imminent append — a zero-novel table writes no marker row and no facts, F-4's zero-fact corollary at marker grain); (5) the append. A kill between (4) and (5) leaves exactly the marker-without-facts state L-2 constructs. Commit's **last act**, after all N tables: the commit-completion row — decide-then-do (rerun-idempotent), written **unconditionally**, including when every table was zero-fact: the completion row is the zero-fact batch's durable visibility (§6.3, answer 2). **[T-4]** The decide-then-do guard **bounds append-only marker growth** under repeated kills; the derived reads (the [DC-1] DISTINCT, M-2's MAX) are dedup-safe regardless — the guard is growth discipline, never read correctness.

**Ordering read (M-2, binding).** "The feed's latest completed batch" = the commit-completion row with max `(received_at, batch_id)` for the feed. `received_at` is data-borne (ingestion-asserted — the same value D-4's fold ties already trust); the `batch_id` tiebreak is **deterministic-arbitrary** (UUIDv5 carries no temporal order; equal-`received_at` siblings get a stable but meaningless winner, documented so nobody reads order into ids); `committed_at` is provenance only, never ordering.

**Attribute coherence (L-3, binding).** Delivery attributes ride every row — the priced cost of partial visibility (a partial batch has no completion row to join). If they disagree *within one batch* (a write bug), the probe treats the batch as incoherent ⇒ **refuse to drop** — never pick a row to believe. The disagreement golden is a §13 obligation (ADR-OQ5 validation 3). **L-3 binds both marker consumers, not the probe alone [AE2-1]:** read 1's resolution names **no** predecessor when the *selected* latest-completed batch's own marker rows disagree internally on delivery attributes — the asymmetry otherwise poisons the ordering read itself (a corrupted `received_at` on a completion row can *win* the max-selection precisely because of the corruption, and a successor dropping against a wrong predecessor is a **silent wrong drop, the forbidden direction**); everything-novel is the priced keep. Mechanics §7.2 read 1; the read-1 golden variant rides K-07.

**Ledger evolution (L-4, binding).** Additive-only — item 20 landed it; row grain unchanged; control never gains a ledger read.

**[DC-1] discharge — the derived probe read (specified here; the check itself is 006.1's).** `committed_tables(batch_id)` = the distinct `table_name` of guard-twin rows for `(batch_id, stage = 'commit')`, sentinel excluded — a single-partition read under §6.4's `identity(batch_id)` (a metadata-only miss for fresh batches). Marker-first means the set can **over-include** a table whose append never landed — the refusal then over-refuses, the permitted direction. Bind refuses **`bind-defect/fact-type-removed-in-flight`** when `committed_tables(batch_id) ⊄` the deployed spec's fact-table set. The check's site in the bind inventory — beside 006.1 §5.6's "bind never reads data" stance, of which this is the one ruled exception (ADR-OQ5's fail-fast closure) — is **006.1's ground, registered as a proposed erratum row (§16), never designed twice**. The door-enumeration union stays rejected (ADR cite); 009's runbook precondition stays defense-in-depth — the +e3 note's required input is hereby **consumed**, not merely restated.

### 5.2 F-2 mechanics — the one derivation function and its two gates

**Function (normative):** `spine/core/identity.py::derive_record_key(key_values) -> str`

- **Input domain:** a mapping of *every* declared `record_key:` column name to its typed value — `str | int | Decimal | date | datetime(aware) | bool | None`, or the value's canonical-string pre-rendering (fragment 2 above). All declared key columns present, always; passing a subset or superset is a caller bug (the map's key set is fixed at bind from the declaration).
- **Output:** `sha256(canonical_json(key_values).encode("utf-8")).hexdigest()` — 64 lowercase hex. Implementation-wise this *is* `core.canonical.row_hash` applied to a third subject; it is declared as its own named function because the seam is the name + subject contract, and because 006 D-6's law — **one shared function, two call sites, never a second implementation** — attaches to this name. Plain-value pure, stdlib-only, no Spark, no pydantic: both the commit-side UDF (F-1, §5.1) and the post_check shaper (`frames/quarantine.py::shape_post_quarantine`, 006.1 §10) wrap it.
- **Totality:** total over complete maps. `None` renders as canonical `null` — a value, not a refusal. Column *names* participate in identity (the hashed object is the map, not the value tuple): a declared key-column rename changes every `record_key`, which is correct — a rename is a breaking declaration change and, under additive-only evolution, a new table.
- **Declared order is irrelevant:** canonical rendering sorts keys bytewise; reordering `record_key:` in the declaration does not change derived keys (pinned by `basic.json`).

**The two call sites and their gates** (the gate is policy, owned per-site; the function never gates):

| post_check quarantine writer (006.1 §10) | derive **iff every declared key column is non-null**, else `record_key` NULL — 006 D-6, cited | never derived — publishing an identity that collides across genuinely distinct identities into the remediation queue is worse than no identity (006 D-6's argument; the divergence from commit's totality is D-6's accepted floor, not an inconsistency) |

CI obligation (deferred §13): `derive_record_key` must reproduce every vector.

**Synthetic-only rule [DS-5] (normative, at +e4):** the provenance rule above constrains the generation *tool*; this rule constrains its *inputs* — vector values must be **fabricated, never derived from partner deliveries or lake contents**. "A real row that failed" is never a test vector: committing real partner/member key material — the values *and* their `record_key` hashes — into a git repository gives it a far broader audience than the lake's IAM posture permits. All 25 committed vectors were verified synthetic at the `conveyer-hpp.6` gate; the rule is a **fixture-review checklist item beside the reproduce-committed-vectors gate**, and its generalization to every tagged-JSON fixture family is proposed as a 005.1 §15.2 convention amendment (§16's row).

**Authoring note (009's register, beside F-6's string-ordering trap) [AE-10]:** byte-distinct but visually identical key material (NFC vs NFD) is **distinct identity by design** — the derivation performs no unicode normalization; a feed whose upstream toolchain changes normalization forms silently re-keys, and the remedy is upstream normalization discipline, never a normalizing derivation.

### 6.3 The marker table

Name and placement: **`<lake db>.<slug>__markers`** — spine-owned *shape*, per-pipeline *instantiation* (quarantine's pattern): one marker table per pipeline, not per type — the `table_name` column carries the type dimension. The own-slug prefix means I-21's existing grant pattern covers it with **zero new IAM objects**, and cross-pipeline marker forgery is excluded by [S-5]'s per-table grants (a pipeline writes only its own markers; delta resolution, the OQ-2 probe, and the [DC-1] bind probe read only own-feed rows; 008's registered readers union across pipelines under their own role). Iceberg v2, partitioned **`identity(batch_id)`, no sort order** (F-3 — ADR-OQ6 settled the marker in-scope: its probes are absent-batch-heavy, precisely the metadata-miss case).

| Column | Type | Nullable | Meaning |
|---|---|---|---|
| `batch_id` | string | no | partition key; idempotency key part 1 |
| `feed_id` | string | no | resolution scope — "latest completed **per feed**" |
| `stage` | string | no | `commit` (day one); fold rows reserved as additive accretion (L-2) — key part 2 |
| `table_name` | string | no | guard-twin rows: the fact table appended; completion rows: the sentinel **`-completion-`** (answer 1 below) — key part 3 |
| `snapshot_id` | long | yes | **NULL on every Phase-1 row** (resolution below); ships now so 008's reserved accretion is additive row kinds, never a migration |
| `delivery_key` | string | no | denormalized on every row (L-3); partner-derived — classification per answer 3 |
| `delivery_content_hash` | string | no | the delivery's `content_hash` from the seed, renamed per ADR-OQ2 (the lane's per-record `content_hash` would confuse someone at 2am); every row |
| `received_at` | timestamptz | no | **the ordering key** (M-2, data-borne; the seed's value); every row |
| `committed_at` | timestamptz | no | provenance only, never ordering (M-2): the writing effect-point's own clock — on marker-first guard-twin rows it *precedes* the fact append's commit by construction, named so nobody reads commit time out of it |

Two row kinds, discriminated by `table_name` alone: **guard-twin** (one per `(batch_id, 'commit', fact_table)` that actually appends) and **commit-completion** (one per batch). **Append-only under the fact-table IAM regime** (M-1 — 007 D-6's write-path law applied verbatim: marker rows are facts, "latest completed" is a derived read, and an UPDATE-capable marker is a mutable pointer that reopens the silent-staleness hole) — **M-1's IAM phrasing scoped per §6.1's [DS2-1] rule**: IAM yields physical no-delete + cross-pipeline isolation; the own-lane writer's `glue:UpdateTable` + `s3:PutObject` suffice for a logical rewrite snapshot, so own-writer append-only on this table is the same named residual at I-21's authored-code/CI boundary (ADR-OQ1's M-1 text carries the matching annotation — §16's row). The scoping is load-bearing here, not decorative: **read 1's soundness and N-4's "genesis-complete ⇒ Track E provably absent" rest on marker history being intact**, and a logical rewrite of marker partitions is exactly the silent-staleness hole M-1 exists to close, re-entered through the writer's own role — which is why the marker table sits in the 008 snapshot-operation audit's strictest class (§16's [DS2-1] row: alarm on **any** snapshot operation ≠ append), the residual's detection layer. **Never pruned in Phase 1** (N-4 — the genesis-complete record is what earns "no key-match ⇒ Track E provably absent"; if retention is ever introduced, a probe lookback exceeding the horizon reads as *unknown* ⇒ refuse to drop; registered to 008 as a retention **prohibition**, not a duty). Writes are guard-idempotent and marker-first (M-3/L-2; write mechanics §4.3). One priced read: the OQ-2 key-match probe scans across partitions by `delivery_key` — accepted (rows are tiny, one table per pipeline, N+1 rows per batch; column stats on `delivery_key` aid the scan), while every batch-keyed probe gets the metadata-miss economics.

**The three explicit answers:**

1. **`table_name` on completion rows — sentinel, not NULL.** The idempotency key is `(batch_id, stage, table_name)`; a NULL component turns the decide-then-do presence probe and every anti-join into `IS NULL` special cases (the null-join trap). The sentinel **`-completion-`** keeps the key total — and needs **no reserved-name rule**: it sits structurally outside 004.1 §6.7's identifier grammar (leading dash), so no declared fact table can ever collide with it — by grammar, not by convention.
2. **Zero-fact visibility.** Guard-twin rows twin **actual appends only** — the twin is written after `delta_filter` (§4.3), so a type whose novel set is empty leaves no guard-twin row and no facts (the twin never lies **within one attempt** [AE2-3]; F-4's zero-fact corollary at marker grain). **Across attempts the claim narrows [AE2-3]:** a twin written by a killed attempt (§4.3 steps 4→5) whose rerun then finds **zero novel under a moved predecessor set** never receives its append — a **stale twin**, permanent under append-only, even after the batch converges (the rerun's completion row lands unconditionally, so read 1's coherence clause never fires on it; the batch resolves as a lawful predecessor whose facts for that table are simply absent — the vacuous-comparison keep, per table). Priced, not new: it is exactly [DC-1]'s named over-inclusion (§4.3 — `committed_tables` may over-include a table whose append never landed ⇒ over-refusal, the permitted direction). The commit-completion row is written **unconditionally** as commit's last act — including when every table was zero-fact — and **is the zero-fact batch's durable visibility**: ADR-OQ1's "including for zero-fact batches", the property no other artifact provides (such a batch is invisible in the fact tables and lossy in the ledger).
3. **`delivery_key` classification.** Partner-derived string (`delivery_content_hash` shares the partner lineage): both ride the **DS-4 / 006.1 §16.9 classification-tagging obligation** — ADR-OQ2's priced negative, honored here — and any ops/queue projection of marker rows is governed accordingly (012's register discipline, the same rule quarantine's lineage columns carry). **[DS2-3]** The 004.1 [S-8] cross-cite, made load-bearing: `delivery_key` embeds **partner-chosen filenames** ([S-8]'s named surface), and the 009 onboarding rule [S-8] registers — *partner filenames may not encode personal data* — is still **unlanded**; under N-4's never-pruned posture this table retains filename-derived material permanently by design, so that rule is a **precondition of the posture, not adjacent hygiene** — `conveyer-4ot.41` must weigh it (§16's Track B row), and 009's authoring register carries it as an onboarding gate (§16).

**`snapshot_id`, resolved at field level.** ADR-OQ5's Option D text carries both "`snapshot_id` … already in hand at write time" (written before the review) and the review's **marker-first hardening** (L-2, named load-bearing at adoption). At field level they cannot both hold for a guard-twin row: written marker-first, the append's snapshot does not yet exist. **L-2 wins** — and the ADR's own accepting clause ("over-refusal and completeness niceties are the price") covers the consequence: Phase-1 guard-twin rows carry `snapshot_id = NULL` by write-order necessity; completion rows carry NULL because one row cannot carry N per-table snapshots without a map (disqualified by L-2). No live consumer needs the value — resolution keys on completion rows, both probes key on presence, and delta reads pin their own snapshots (§4.2). The column exists so the **durable as-of home the ADR reserves to 008** (fold rows / snapshot-bearing accretion) lands as additive row kinds; until then as-of rides D-5's existing channel (the ledger's `snapshot_ids_by_table` — attempt-truth, allowed lossy — plus the 30-day stamped summaries), unchanged.

### 6.4 F-3 — the three partition specs

**Fact tables and the marker table: `identity(batch_id)`, no sort order — ADR-OQ6, transcribed.** Every correctness-path read is `batch_id`-keyed (guards/doors every attempt; `read_batch` and delta reads every batch; anti-joins every rerun); absent-batch probes become metadata-only misses; [T-9] dissolves structurally — each partition receives exactly one append and is never written again, so fact-table compaction approaches moot (008's row shrinks to cardinality review + optional within-partition merges); one append = one partition under I-4's bound. The composite spec stays disqualified (scatters one append across buckets); the 001 §6 departure is recorded as an erratum in this same change, its `bucket(domain_id)`+time instinct re-aimed at the state tables below. **PS-1…PS-3 are carried verbatim as binding invariants:**

> **PS-1 — Layout serves the process side; perception rides stats and evolution.** The fact-table spec is chosen for the `batch_id`-keyed reads that run every attempt. Analytical pruning rides Iceberg column stats; if measured query patterns demand more, the answer is **additive partition-spec evolution owned by 008's review** — not a fact rewrite, and never a return of [T-9]-style clustering discipline. *Precision on the no-rewrite stance*: a content-preserving Iceberg rewrite violates no law — facts are values, and a rewrite preserving every row changes no fact. Forgoing rewrites is a **choice**, made on economics and erosion risk (rewrites are exactly where [T-9]-style discipline holes re-enter). Stating it as a choice cuts both ways: nobody later "corrects" PS-1 as a misreading of the immutability law, and nobody invokes that law to block a rewrite the data genuinely justifies — such a rewrite needs a decision record weighing the erosion risk, not an exemption from law.
>
> **PS-2 — `identity(batch_id)` is the leading transform, and append-locality is load-bearing.** Any future evolved spec keeps the guard probe a partition-level operation and must re-argue the small-file bound: a transform that scatters one `(batch, table)` append across partitions (bucketing, fine-grained time) re-creates Option B's disqualification for all data written after it and needs its own decision record, not a config change.
>
> **PS-3 — Facts and state do not share a layout by analogy.** The two table classes have opposite hot profiles (process-keyed vs domain-keyed). F-3's state-table ruling weighs `bucket(domain_id)` on the MERGE profile on its own merits; neither ruling is precedent for the other, and the 001 erratum says so — the sketch is re-aimed, not refuted.

The accepting clause — forward-only reversibility priced, with **[PB-1]**'s measured numbers (probe bead `conveyer-hpp.13.11`, ADEQUATE under the pre-stated rule) landed in it — is F-2-adjacent house form and lives in F-3's Y-statement (§2), not duplicated here; the 008 register-row consequence is §16's v0.4 block.

**State tables — the own-merits ruling (PS-3 forbids analogy).** The hot profile, stated: (1) **domain-keyed MERGE every batch** — I-11's slice-fold: touched-set semi-join, then the conditional MERGE under merge-on-read; (2) **full-scan/overwrite rebuild** — D-5's run mode through F-7's same-lineage conditional swap (RB-1); (3) **read-only consumers** — the domainDB cross-materialization on `batch-completed`, occasional Athena point/period reads. Candidates:

- **S-0 — coarse identity partitioning: structurally unavailable.** [H-6] DDL is generated mechanically from the declaration; the only framework-guaranteed columns are `domain_id_col` and the stamps. `identity(domain_id_col)` is one partition per row (partition count = live domain count — metadata explosion); no low-cardinality column exists generically, and a per-feed authored partition column is 009-surface growth with no Phase-1 customer. Disqualified before comparison.
- **S-A — `bucket(domain_id_col, N)`** — 001 §6's re-aimed instinct, weighed where it belongs.
- **S-B — unpartitioned, declared sort order on `domain_id_col`.**

| Criterion | S-A — `bucket(domain_id, N)` | S-B — unpartitioned + sort order |
|---|---|---|
| MERGE target scan (the hot read) | bucket pruning pays only when touched-count ≪ N; a full-restatement feed — the resident class — touches every bucket every batch: pruning ≈ zero exactly where the cost lives | full scan of a table whose row count = live domain count (bounded, orders below the fact tables); sort clustering gives file-stats skips between compactions |
| Write shape per fold | delete + data files scattered across up to N scopes per MERGE — small files multiplied by the spec itself (the shape that disqualified ADR-OQ6's Option B, one table class over) | one scope; file count = writer tasks; compaction single-scope |
| The knob | N chosen now, without the volumes 008's review will have; a wrong N is a spec evolution + rebuild anyway | no knob |
| Rebuild / RB-1 | compatible (a full overwrite lays into buckets; the same-lineage conditional swap is spec-agnostic) | compatible; the overwrite is one commit, one scope |
| Reversibility | evolution + next rebuild re-lays everything | the same instrument — adopting S-A later, with 008's measured data, is one additive evolution + one rebuild; **state-table layout reversibility is total, not forward-only** (the rebuild that already exists re-lays all data; the fact-table caveat does not transfer) |
| Concurrent-sibling MERGE conflicts | disjoint-domain siblings share fewer files ⇒ fewer false serializable conflicts | coarser conflict granularity ⇒ more false conflicts — absorbed by I-11's existing retry path; efficiency, never correctness; no cause to narrow isolation [T-10] |
| Readers (domainDB upsert, Athena point reads) | bucket pruning for point lookups | sort-order stats pruning; decays between compactions — restored by the compaction merge-on-read already makes constitutive (D-5's accepted trade): a table-metadata instruction to a job that must run anyway, never a new [T-9]-class remembered rule |

**Winner: S-B — unpartitioned with a declared sort order on `domain_id_col`.** Bucketing prunes nothing on the resident hot profile while multiplying files on every fold and demanding a knob without data; S-B's simplicity is fully reversible because state's rebuild re-lays the entire table under whatever spec is current. Neither constraint breaks: RB-1's same-lineage swap is table-metadata-agnostic, and the MERGE profile keeps merge-on-read + serializable isolation exactly as I-11 pinned them. **Sort-order honesty:** the declared order is best-effort at write and restored at compaction; correctness never reads it (it aids stats pruning only) — a fold MERGE whose output lands unsorted is not a defect.

### 6.5 Bootstrap — `spine/bootstrap/create_record_tables.py` — and F-10 mechanics

`create_record_tables.py --spec-uri <pipeline spec> [--catalog spine_cat] [--env …]` — idempotent, 005.1 §4.4's idiom mirrored exactly: one parser (the `PipelineSpecModel` path), driver-side Spark SQL DDL, run by the **deploy principal**, never the job role.

Never drops, never retypes, never reorders (additive-only, 001 §7, enforced here rather than reviewed-for).
3. **Per type — state table:** same discipline per §6.2, plus **assert-and-repair `write.merge.mode = merge-on-read`**: a present table with the wrong mode is repaired (`ALTER … SET TBLPROPERTIES`) with a loud log line, never tolerated — errata #9's failure shape is *silent* no-op-signal loss, exactly what an unrepaired drift would reinstate. **`write.merge.isolation-level = serializable` is asserted-and-repaired beside it [DC2-3]** — §9.2's registered extension, landed: the straddle detection leans on this property, and a drift to `snapshot` would silently narrow I-11/RB-2's conflict surface (errata #9's failure shape, one property over). 4. **Marker table:** create-if-absent from the constant DDL (§6.3); if present, exact-schema assertion (quarantine's rule — the shape is framework-owned; a diff means a framework upgrade forgot its own migration note; fail loudly).

The `marker` value is **a value C4 refuses as a co-effect by construction** (C4 accepts only `state`); the enum extension `{raw, quarantine, facts, state, run-ledger, marker}` is a 006.1 §5.2 text edit — proposed erratum row, §16.

### 7.1 F-4 mechanics — N guarded appends, per-(stage, table) grain

- **Iteration:** commit walks the declared fact-type set in declared order (total, deploy-pinned; the declaration surface is 006.1 P-1's). Per table: **decide-then-do** — `table_has_batch(fact_table_t, batch_id)`; if present, skip *that table* (`facts_appended[t] = 0`, snapshot resolved by stamped summary per I-19); if absent: structural check (§7.3), `delta_filter` for that type (F-5, §7.2), exactly one `append`. ### 7.2 `delta_filter` — F-5

Register sources: **ADR-OQ1 / ADR-OQ2, both Accepted — transcribed, never re-argued** — plus ADR-OQ5's L-3; the baseline is 007 D-2, whose seam contract, fail-open law, and accepted residuals this section restates only at the new grain. The declaration surface is 006.1's; door semantics are 006.1 §8's (cited at §7.1 — this section adds no door behavior); supersession *adjudication* is 002.1 §8.3's (cited only — the authority seam, N-1).

**The pure plan, per type (D-2's seam at F-4's grain).** `frames/delta.py::delta_filter(candidates_t, predecessor_facts_t) → novel_t` — a pure plan builder (I-9's zone); the framework owns every read, the filter reads nothing. Semantics per D-2, cited: (a) **within-batch collapse** on `(record_key, content_hash)` — **unconditional**: it runs even under a probe refusal ("drops nothing" means *delta* drops; N identical in-batch assertions are one fact, not N); (b) divergent within-batch duplicates both commit (the observable-data condition, D-2(b)); (c) a candidate **drops iff, per `record_key`, its `content_hash` is unchanged in *every* batch of the resolved predecessor set** — one batch normally, two when Track E applies ("in addition, never instead"), zero ⇒ everything novel. `record_key` is the join identity (F-2, §5.2) and `content_hash` the compared value (F-1) — identity joins, value compares, never complected (§5.1 fragment 1). The filter runs at §4.3's step (3), after F-1's stamping and §7.3's structural check, before the guard-twin decision (the twin is decided *after* the filter so it twins an actual append — §4.3, cited). `predecessor_facts_t` = the resolved batches' partitions of fact table *t*, projected to `(record_key, content_hash)` — single-partition reads under §6.4's `identity(batch_id)`, **one pinned snapshot per table**, recorded into `delta_read_snapshot_ids` (both predecessor batches live in the same table; one pin covers both — §4.2, cited).

**Resolution and probe run once per batch.** `core/delta.py::resolve_predecessors(seed_attrs, completion_rows, presence_rows, target_rows) → PredecessorResolution` — a pure, **total** decision over framework-read plain values (the marker reads are the effect layer's; `RunnerFx` accretes the marker read members additively, 004.1's record-of-functions idiom). `PredecessorResolution` = frozen `{predecessor_batch_ids: tuple[str, ...], probe_refusal: str | None}`, projected set-once into §4.2's slots. One resolution, one probe verdict, N per-type filters consuming it. A **failed marker read is a stage failure (retry), never a refusal** — refusals are adjudication outcomes, errors are errors; there is deliberately no fifth reason code for infrastructure. The three marker row-set reads (completion, presence, target) need **no shared snapshot pin [AE2-9]**: every split-read interleaving — a completion or twin landing between reads — degenerates to either the named completion-after-resolution residual (D-2's accepted core, read 1 below) or an over-refusal, the permitted direction; contrast the fact reads, which pin and record (§4.2) because value comparison must be reproducible.

**Read 1 — the derived latest-completed (ADR-OQ1; M-1…M-3 binding).** Latest completed = the feed's commit-completion rows, **self-excluded** (a rerun's own completion row is not a predecessor), max `(received_at, batch_id)` — §4.3's ordering read, cited never restated (M-2 data-borne; deterministic-arbitrary tiebreak; `committed_at` never ordering; writes guard-idempotent, M-3). **The coherence clause (ADR-OQ1's soundness argument, transcribed):** if any same-feed batch (self excluded) shows guard-twin presence with **no** commit-completion row — a kill-in-commit or an in-flight sibling — resolution names **no predecessor** (empty set ⇒ everything novel, recorded as such in `delta_predecessor_batch_ids`). L-2 makes this sound *by construction*: marker-first means facts-without-marker cannot exist, so every batch whose committed facts a wrong drop could interact with is visible to this clause; the inverse kill state (marker-without-facts) merely over-refuses — the permitted direction. D-2's concurrent-sibling residual thereby **narrows to its named core** — a sibling completing *after* resolution ran (accepted there, unchanged); the completion-absent half is now visible and refuses. **The L-3 extension into read 1 [AE2-1] — the winner must cohere:** the selection is only as sound as the attributes it orders by, and a completion row whose `received_at` disagrees with its own batch's guard-twin rows can *win* the max-`(received_at, batch_id)` read *because* of the corrupted value — a successor then dropping unchanged-vs-that-predecessor is a **silent wrong drop, the forbidden direction**. So resolution names **no** predecessor when the selected latest-completed batch's marker rows disagree internally on delivery attributes (L-3's rule applied to read 1's winner — never pick a row to believe; everything novel, the priced keep, recorded as an empty `delta_predecessor_batch_ids`). A pure-function change only: the winner's full row set already flows into `resolve_predecessors` (`completion_rows`, `presence_rows`) — **no new read**. The read-1 golden variant rides K-07.

**Read 2 — Track E (ADR-OQ2 Option D; N-1…N-4 binding).** The seed's `supersedes_batch_id` (`DeliveryRegisteredV1`, 004.1 §6.1 — once `conveyer-kof` lands, below) is the **only adjudicator**; the probe detects, in both directions (N-2), keyed on the seed's own delivery attributes (`delivery_key`, `delivery_content_hash` — §6.3's marker columns, same source):

- **Field None/absent** — scan marker **presence**: any row kind, completed *or* partial, self excluded, carrying the seed's `delivery_key` with a **different** `delivery_content_hash`; any hit — **or** any candidate batch whose own attribute rows disagree internally (L-3: incoherent, never pick a row to believe) — ⇒ refuse, reason **`none-with-key-match`** (a coherent "no key-match" could not be affirmed). No hit against the genesis-complete record (N-4: never pruned in Phase 1, §6.3) ⇒ Track E **provably** absent ⇒ one-read is lawful.
- **Field names a target** — read the target's marker rows (single-partition; metadata-only-miss economics, §6.4). No rows at all ⇒ **`target-unmarked`** (N-3: absence is *unknown*; bites pre-marker targets **and targets killed before their first marker write** — the former self-extinguishing, the latter transient, clearing on the target's rerun [AE2-4]). Rows present but `delivery_key`-incoherent with the superseding delivery, or internally disagreeing (L-3) ⇒ **`target-incoherent`**. Coherent agreement ⇒ the second read runs exactly as D-2 states: predecessor set = {latest completed, named target}, the target's facts read directly at their pinned snapshot.
- **`horizon-exceeded`** ships in the enum (§4.2 already names it) but is **unreachable in Phase 1** (never-pruned, N-4): if retention is ever introduced, a probe lookback exceeding the horizon reads as *unknown* ⇒ refuse — reserved now so the rule is priced, never retrofitted (M-3's strengthened form, cited at §6.3).

**N-1, the standing audit (binding).** The probe never nominates a superseded target; **no code path in this lane computes, infers, or selects a supersession target from data** — the seed field is the only source of a target, the probe's only outputs are the four reason codes, and its only action is widening the keep-set. A probe that selects has rebuilt ADR-OQ2's Option C by stealth. The audit is grep-shaped: `resolve_predecessors` takes the target *in* and never returns a batch id it was not given (read-1's resolution excepted — that read names the *latest-completed*, an OQ-1 question the probe never touches).

**The trust residual, named beside D-2's [AE2-5].** N-1's detection is keyed on delivery attributes, so a target that is **coherent but wrong within the same delivery-key chain** — the field names a batch carrying the *same* `delivery_key` that is not in fact the superseded one — is **undetectable by design**: the attributes agree, both reads proceed, and the resulting drops stand or fall with what §8.3 asserted. Supersession correctness inside a key chain rests on **002.1 §8.3 alone** — the single-authority seam ADR-OQ2 chose (the alternative was Option C's forked adjudication, rejected). Named beside D-2's accepted residuals, not asserted away: this lane's own guarantee is confined to cross-chain incoherence (N-2's both directions) and the four refusal reasons.

**Refusals are data (the ADR's F-5 obligation, discharged).** A refusal is **batch-grain**: `delta_probe_refusal` set once (§4.2's slot, enum verbatim); non-null ⇒ every per-type filter short-circuits to keep-all (after the unconditional in-batch collapse). Channels: the commit ledger row carries the reason (additive projection through `core/run_facts.py` — L-4 / item 20's class; observability, never control — L-1 untouched) and EMF **`DeltaProbeRefusals`**, reason-dimensioned, emitted at the effect point. **Value-free ([S-7]/[S-18]):** the reason code is the *entire* payload — no `delivery_key`, no `delivery_content_hash`, no batch content ever appears in a reason, a metric dimension, or a log line (the columns' own classification is §6.3 answer 3's ground; the channel stays clean). The dual of "never silent drops" is **never uninspectable keeps**: a refusal is safe but *symptomatic* — of the §8.3 race, a marker-write bug, or a misbehaving field — and the alarm-worthy signal is a **persistent nonzero rate on one feed**.

**The interim floor and the bootstrap residual (carried verbatim, not asserted away).** Until the field lands, every batch is supersession-unknown and the probe floor alone is lawful *for content post-dating the marker table*: no key-match against the genesis-complete record ⇒ Track E provably absent; key-match ⇒ refuse. ### 7.3 F-8 mechanics — the I-24 backstop vs. the demoted implicit check

**The check (per-table):** before each fact table's append — (a) `domain_id` non-null on every row of that type's admitted frame; (b) pure column-set diff against that table. Violation = named defect, fail fast, no append, no fold — 004.1 I-24 unchanged in mechanism, applied per table in F-4's loop.

**Why demoted rows never reach it — the argument, path by path** (the demotion: 007 D-3(d) routes data-borne NULL `domain_id` to quarantine via 006 D-6's implicit check, evaluated before all authored checks):

1. **Fresh path:** `admitted = candidates` bag-subtracted against the in-memory violations (006 §5.4 [DC-5]); the implicit check fires on every null-`domain_id` row, so every such row is in the subtrahend. None survive to commit.
2. **Guard-present rerun:** admitted = recomputed candidates anti-joined against the durable `row_hash` set for `(batch_id, "post_check")`. The implicit check is value-determined (null-ness is a function of the row value), so a recomputed null-`domain_id` candidate hashes identically to the durable quarantine row the original attempt wrote, and subtracts. None survive — **under unchanged inputs. The drift qualifier [AE-3]: the anti-join consumes only rows the original attempt adjudicated.** A rerun re-resolves current co-effect snapshots (D-2's rerun bullet), and a drifted co-effect can make `apply` emit a **new** NULL-`domain_id` candidate the original attempt never produced: no durable hash matches it, it survives the subtraction into the admitted frame, and it reaches the backstop through DURABLE_SUBTRACT — a second reaching path beside path 3, with the same closure (named defect, no append; drift or defect, never data). The batch is then deterministically wedged while the drifted co-effect state persists; 006.1 §11 maps the row and its remediation (corrected delivery/supersession, or co-effect correction, then rerun).
3. **The residual — and why the backstop stays:** the durable-authority doors (006.1 §8's ground: quarantine guard absent + facts present ⇒ empty violation set, *no check evaluation*, all recomputed candidates admitted). Construct the reaching path: an N-type batch killed between type appends (table A has facts, table B does not) is rerun under drifted co-effects or a moved deploy pin; the door fires on ANY-table presence, admitting an **unevaluated** candidate set; table B's guard is absent, so its append proceeds — and a drift-born null-`domain_id` row in type B's frame *would commit*, then be re-INSERTed by every subsequent fold of table B, silently and forever. The backstop converts exactly this into a named, deterministic defect.

**Placement statement, in one line:** the candidate-seam implicit check owns *data* (routing, attribution, `business/missing-domain-id`); the commit-stage backstop owns the *invariant* — its firing is never data routing but always a defect (a framework bug, or drift reaching commit through a durable-authority door), and the demotion narrows neither its `domain_id` half nor its schema-diff half. 006.1's failure map cross-cites this section; this doc's full per-type kill matrix is §11's.

### 8.1 F-6 mechanics — the ordering-comparability set

| Type | Order semantics | Notes |
|---|---|---|
| `int`, `long` | integer order | |

| `date` | chronological | |

### 8.2 MERGE plans, intra-batch reduce, no-op detection, cardinality defect

**The per-type plan (normative).** For each declared fact type, in F-4's iteration order, fold builds one plan from the type's `MergeSpec` (§4.1): (1) read the batch's committed facts for the type — a single-partition read under §6.4's `identity(batch_id)`; (2) the **intra-batch reduce** — one winner per `domain_id` under §8.1's comparison; (3) the **conditional MERGE** of winners against the state table — `WHEN MATCHED AND <strictly-greater> THEN UPDATE SET <update_cols>` (the winning fact carried whole, §4.1's mechanical column set), `WHEN NOT MATCHED THEN INSERT *`; (4) own-commit resolution and no-op detection. Steps 1–3 are pure plan builders; the framework owns execution and commit (I-9's zone; 004.1 §6.7's identifier validation and `_conveyer_merge_src` unchanged, not restated).

**The reduce (D-3(a)'s first application).** `frames/fold.py::reduce_batch_winners(facts_df, spec) → winners_df`: `row_number()` over `PARTITION BY <domain_id_col>` ordered by every ordering element **descending with an explicit `NULLS LAST` directive per element** — [T-11]'s null-ranks-lowest rendered on a *documented* sort surface, never inferred from engine comparison internals — keeping rank 1. The reduce is mechanical necessity, not optimization: Iceberg MERGE raises on duplicate source matches, so an unreduced source is a defect. Determinism needs no arbitrary tiebreak: within a type, [T-12]'s grain law makes `record_key` and `domain_id` coincide (D-3(c)), and §7.2(a)'s unconditional within-batch collapse has already removed exact `(record_key, content_hash)` duplicates — so two same-domain survivors always differ in `content_hash`, the final ordering element, and a full tie is **unconstructible inside one batch**. (Divergent duplicates — same key, different hash, both committed per D-2(b) — are exactly the rows the hash tiebreak adjudicates: deterministic, semantically arbitrary, remediated by a corrected delivery; counted at §12.)

**The rendering decision — explicit field-wise expression, never native struct comparison (normative).** §8.1's comparison is rendered at the MERGE site as an **explicitly generated field-wise boolean**, built purely from `MergeSpec.ordering_cols` by `core/merge.py::ordering_predicate(spec) → str` (a pure SQL-text builder over 004.1 §6.7-validated identifiers, consumed by `effects/spark.py::_build_merge`): per element *e*, `gt_e ≡ (t.e IS NULL AND s.e IS NOT NULL) OR (s.e IS NOT NULL AND t.e IS NOT NULL AND s.e > t.e)` and `tie_e ≡ s.e <=> t.e` — every term rendered **three-valued-total** (never evaluating to SQL `NULL`, so the chain's truth value never leans on `NULL`-propagation coincidences) — chained lexicographically: `gt_1 OR (tie_1 AND (gt_2 OR (tie_2 AND … gt_k)))`; the last element is `content_hash`, never null (F-6), so the order is total and a full tie renders the condition false — the no-op. **Rejected: native struct/tuple comparison (`(s.e1, s.e2, …) > (t.e1, …)`)** — its null ordering inside comparison is *engine implementation behavior, not documented contract*: pinning [T-11] to it moves the normative semantics out of the artifact and into the engine, an out-of-band contract in exactly the place a Spark version bump could silently flip fold winners — a **silent wrong-state class, the forbidden direction** — where the explicit rendering fails loudly at analysis if surfaces move. The probe evidence sharpens this: the F-7 kernel probe's own tuple-comparison MERGEs (bead `conveyer-hpp.13.10`, A2/A3) ran on **never-null fixtures**, so the null region — precisely where [T-11] and struct comparison can diverge — is verified by *no* probe. **The engine pin, registered to §13:** the MERGE-condition builder and the reduce's sort directives each ≡ one plain-Python reference comparator implementing §8.1's table, differentially tested over generated element values *including nulls per element type*; native struct comparison may not be substituted at either site unless it first passes the same differential — the two-evaluators discipline (005.1 A-7's) applied to comparison. Accepted cost: generated verbosity (O(k) terms, k single-digit by declaration), and two rendering sites (sort directives at the reduce, boolean at the MERGE) aligned by the one differential property — never by review. **[T-1]** The K-14 differential has since run on the pinned stack (Spark 3.5.9): native struct comparison **agreed** with the reference on all 9219 generated cases (7922 null-bearing) — the rejection **stands on its stated ground** (null ordering is engine implementation behavior, not documented contract; a single-version probe cannot pin future versions or engines); the agreement fact is recorded so a later differential-runner does not mistake it for a reopening argument.

**No-op detection, per table (errata #9, at F-4's grain).** After each MERGE: resolve the own-commit snapshot as the unique child of the pre-statement `before_id` (errata #8's mechanics, per state table) and read its summary; the table's fold is a **logical no-op iff `changed-partition-count = "0"`** — never by diffing snapshot ids, because Iceberg MERGE **always physically snapshots** (errata #9, re-confirmed at engine grain by probe A3), and reliably only under `write.merge.mode = merge-on-read` (§6.2's bootstrap-enforced DDL law — copy-on-write silently loses the signal). Projection (§4.2/item 20 consistency): a no-op table records `rows_merged_by_table[t] = 0` and **omits** its key from `fold_snapshot_ids` — "absent key = no-op" stays true even though a physical child snapshot exists (discoverable via table history if ever needed); a rerun that no-ops everywhere is legible from the maps alone. Errata #8's third state (`attributable=False` — a sibling landing between base-capture and our MERGE) is unchanged and informational: correctness never reads attribution.

**The cardinality defect ([T-12], named).** Spark's `MERGE_CARDINALITY_VIOLATION` is detected off the wrapped Java exception and re-raised as the named `ValueError` ("fold cardinality defect … I-11 [T-12]") — deterministic, never `TransientError`, retry wasted (errata-notes §2-007, `conveyer-nvh.36`; consumed verbatim at the per-type grain: the defect names the state table). And the reduce sharpens the diagnosis: post-reduce the **source** is unique per `domain_id` by construction, so a runtime cardinality violation can only indict the **target** — the state table already violates its one-row-per-domain grain. Remediation is diagnosis of the writer that broke grain, then a rebuild of that table through §9's run mode — never DML (D-6).

### 9.2 The swap — pin order, the pinned idiom, the retry loop, RB-1…RB-3

**Pin order (load-bearing — an L-2-class write-order rule).** Rebuild captures the state table's current snapshot `before_id` **first**, then pins its fact-table read snapshots. Any batch landing between the two captures then moves state past `before_id` and the swap **refuses** — over-refusal, the permitted direction. The reverse order is forbidden by the construction of the hazard itself: facts pinned first, a batch B folding before `before_id` capture leaves B's facts *outside* the pin and B's fold contribution *inside* the validated snapshot — the swap validates cleanly and erases B. (The ADR's "captures … when it pins its fact read" is hereby sharpened to this order — the same instrument as L-2: ordering chosen so every interleaving errs loud.)

**The commit — one lawful rendering (normative; probe-verified A1).** The swap is `DataFrameWriterV2.overwrite()` carrying **both** options, always:

```python
(rebuilt_state_df.writeTo(state_table)
    .option("validate-from-snapshot-id", str(before_id))
    .option("isolation-level", "serializable")
    .overwrite(lit(True)))
```

Against a state table moved past `before_id` this raises `ValidationException` ("found conflicting files") with the live fold's rows untouched and lineage chained (RB-1) — probe A1's observed behavior, verbatim.

**Two forbidden look-alikes (normative warnings — empirical, from the probe, not style):**

1. **`validate-from-snapshot-id` alone is silently ignored** on the OverwriteByFilter path — without `isolation-level = serializable` beside it, the swap **blindly wins**: the forbidden lost update inside an apparently-safe conditional call (negative-tested as probe A1's fragility case).
2. **SQL `INSERT OVERWRITE` has no per-statement options channel** — it always silently wins.

Any `.overwrite(` on a state table missing either option, and any SQL overwrite of a state table, is a defect — a grep-shaped audit in N-1's mold, stated here so the rule exists from this revision; §15's checklist gathers it (its final row).

**Refusal → re-pin → retry.** On `ValidationException`: discard the computed frame, re-capture `before_id`, re-pin facts (now including the interleaved batch), recompute `fold(all)` through the same §8.2 plans, retry. No force path exists (RB-2). Retries are **attempt-truth**: each attempt rides the run ledger (the rebuild stage-vocabulary accretion registered to 004.1, §16) and EMF `RebuildSwapRetries` (§12); the persistent-refusal alarm is 008's row (RB-3, §16).

**The straddle side (I-11, unchanged).** A live MERGE whose base pre-dates the swap raises `ValidationException` ("cannot commit, missing data files" — `validateDataFilesExist`) under the state table's **serializable merge isolation** — no per-statement option needed on the MERGE side; the reliance is I-11's existing one (probe A2) — → `TransientError` → SFN retry → the rerun folds against rebuilt state and converges: pin included the batch's facts ⇒ full ties ⇒ no-op (probe A3, §10 case (c)); pin excluded them ⇒ the retry applies them; correct either way. **The isolation property is load-bearing**: the probe exercised `write.merge.isolation-level = serializable` as an explicit table property; Iceberg's default coincides today, but a property drift to `snapshot` would silently narrow exactly this detection — the §6.5 assert-and-repair extension is registered (§16), the same instrument already guarding `write.merge.mode`.

**RB-1…RB-3 (binding invariants — ADR verbatim in substance):**

> **RB-1 — The swap is lineage-preserving.** Rebuild commits into the state table's own snapshot lineage (Iceberg-native conditional overwrite on the same table identity) — **never** write-new-table-and-rename. Lineage is what makes the swap and concurrent MERGEs mutually conflict-detectable; a catalog rename disables both directions of protection and reconstructs the lost update — and independently breaks as-of perception across the rebuild boundary (§9.5).
>
> **RB-2 — The swap is conditional and never wins by force.** `before_id` captured per §9.2's pin order; the swap validates state is still there; on conflict it fails loudly, re-pins, retries. The retry count rides the ledger like any attempt truth. No `--force` variant exists: a rebuild that must win against live folds is a quiesce problem (RB-3), not a flag.
>
> **RB-3 — Quiesce is efficiency, never correctness.** The "no in-flight batches" check — marker presence without a commit-completion row (§4.3's probe) — belongs to 008's rebuild runbook, to bound retries on busy feeds: defense-in-depth over a constructively closed invariant (the DC-1/AE-7 disposition). **With the blind window named**: marker presence begins at commit — a batch anywhere in land→apply is *invisible* to the probe, so a clean probe is not quiet, only "no batch at-or-past its first marker write" [AE2-6] (visibility begins at the first guard-twin row, mid-commit and marker-first — not at commit's end). Harmless to correctness (nothing on the correctness path reads the probe; the cost is one more swap retry when an early-stage batch reaches fold mid-rebuild) — but a runbook omitting the caveat silently overclaims, so the caveat is part of the registered row (§16), never optional prose. Livelock surfaces as the RB-2 retry metric and its alarm, not as wrong state.

### 9.3 The perception disposition (the ADR's registered 006 D-3 question — **answered**)

A successful swap is a state change no `batch-completed` announced. The disposition, ruled here rather than discovered by a confused consumer:

1. **Tier-2 in-batch rebuilds need nothing new** — a full-rebuild-only pipeline's rebuild *is* its fold stage inside a batch run, and that batch's own `batch-completed` announces it. The gap is exactly the **out-of-band rebuild** (bug fix, operational restatement) — which runs *because* state diverged, so event-gated cross-materializations hold the diverged values and nothing re-announces: the lost-update hazard's perception-side twin.
2. **The announcement is required, and it is an event, never marker rows.** Consumers gate on broadcast novelty (reified process — push, never poll); marker rows are a pull surface, and electing them would put a polling duty on every consumer. The out-of-band run mode emits **`rebuild-completed`** (working shape `RebuildCompletedV1`: pipeline slug, per-state-table post-swap snapshot ids, `occurred_at` — lineage only, value-free) as its **last act** after the swap commits; a kill between swap and emission is §11's row (state correct, perception stale, completed by rerun — the same shape as a batch killed between commit-completion and publish). The event's shape and surface belong to **004.1's event contract** — registered as a proposed erratum row (§16) with 011/domainDB re-materialization and 008's runbook as the named consumers. Until it lands, the out-of-band rebuild runbook carries an explicit manual re-materialization step — **the interim is discipline and says so** (named, not hidden; §16's 008 row).
3. **Rebuild marker rows stay what the ADR left them**: a `rebuild` stage kind under L-2's stage-scoped naming is *reserved* as additive observability if 008 ever wants durable rebuild provenance — **never load-bearing**; Phase 1 writes none.

### 9.4 The write principal (a D-6-class ruling)

Rebuild executes under the **fold's own principal — the pipeline job role**. D-6's state-table law, restated at implementation grain: the job role is the sole writer principal on its state tables, holding exactly two verbs — the fold MERGE and the rebuild's conditional overwrite (**held as one write capability at IAM grain [DS2-4]**: `glue:UpdateTable` + `s3:PutObject` do not distinguish MERGE from overwrite — the two-verb boundary is [DC2-2]'s linter/effects-layer construction, §6.1's [DS2-1] standing rule applied, never a grant distinction); consumers stay read-only; rebuild touches no fact table (its fact reads are pinned snapshots). **Rejected** a separate governed rebuild role: it buys no protection — the job role already holds the stronger *standing* write (a continuous MERGE capability every batch; state is the disposable derivative, and the tables whose immutability is law — the fact tables — grant overwrite to no one); it adds a second ACL surface to provision and audit (F-10's argument class); and it breaks D-3 tier-2, where rebuild is the steady-state fold path — a separate ops-held role would put a human in the routine path. What *is* governed is the **trigger**: an out-of-band rebuild is invoked through the run-mode surface under I-20's governed-escape-hatch class — 008's runbook (§16), never an ambient capability exercised casually.

### 9.5 As-of, restated at implementation grain

- **As-of perception survives the swap because of RB-1, and only because of it.** The swap is a commit in the same lineage, so pre-rebuild snapshots remain ancestors in the same table metadata; the ledger's batch→snapshot mapping (D-5's channel — `snapshot_ids_by_table`, the 30-day stamped summaries) resolves across the boundary unchanged. The horizon is 008's snapshot expiration, exactly as before. A rename-swap would have orphaned every recorded snapshot id — RB-1's second reason, now at the grain where it bites.
- **Honesty note — the swap does not rewrite perception history.** As-of perception answers "what did state look like after batch N" — perception truth. A rebuild motivated by a bug fix does **not** retroactively repair it: "what *should* state have been after batch N" is a re-fold of facts at batch N's pins — a fact-side computation, D-5's two-questions boundary restated at swap grain.
- **As-of business time: untouched.** A query over facts (D-1/D-5); rebuild never writes a fact table.

## 10. The Fold Proof Harness

**Placement: the spine suite** — framework property tests over generated declarations and fact sets (`hypothesis`, 005.1 §12.4's generator idiom; local-Spark substrate per 004.1 §12.1), never per-pipeline: the fold contract is framework law (D-3), and this harness is what earns D-5's claim "state is disposable" on every CI run. **R-07 stays the runtime probe — never the proof**: production sampling detects divergence (a defect page, not a data event); it cannot establish order-insensitivity, and a suite leaning on it has replaced proof with monitoring.

**The core property (D-3, per-type).** For generated fact sets — random domains; declared ordering columns drawn from every §8.1 type **with nulls generated in every nullable element** ([T-11] exercised, never assumed); divergent duplicates included (D-2(b)) — and for random partitions of each set into batches folded in **shuffled arrival orders**: `fold(all facts, one shot) ≡ the incremental fold sequence`, asserted per state table. Named variants on the same generators:

- **Late file** — an older-`received_at` batch folding *after* a newer one: final state identical (the A→B→A litmus's property half; its kill-matrix row is §11's).
- **Concurrent sibling** — two batches' MERGEs interleaved through I-11's conflict-retry path: converge to the same state as any serial order.
- **Per-type** — an N-type declaration: the property holds independently per state table under F-4's iteration order, including a kill between MERGEs + rerun (§11's row, exercised as a scenario).
- **Rebuild equivalence rides the same harness (D-5, verbatim)** — `rebuild(all facts@pin)` ≡ the incremental fold at the same pin: not a separate proof artifact; the same generated sets, one more fold path through §9's swap.

**The three OQ-7 cases (ADR-OQ7 validation 2 — standing regressions):**

- **(a) Mid-rebuild fold.** Rebuild pins (`before_id` first, §9.2's order); a live fold lands; the swap must raise `ValidationException` with the fold's rows intact; re-pin → recompute → converge.
- **(b) The straddle.** A MERGE based pre-swap commits post-swap → `ValidationException` → retry → converges against rebuilt state.
- **(c) Tie-idempotency — the case that carries the post-swap retry's safety.** Batch B committed *before* the rebuild's pin, folded *after* the swap: the re-MERGE must be a logical no-op on full ordering ties, asserted via `changed-partition-count = "0"` on the own-commit snapshot — **never** by snapshot-id diff (the MERGE physically snapshots regardless, errata #9). D-2/D-4's tie discipline is thereby asserted specifically, not inherited silently. Evidence: **probe-verified, bead `conveyer-hpp.13.10`** (Sheet A3 — strict-`>` tie discipline holds at engine grain).

**Probes vs. suite.** The two kernel probes — `probe_oq7_swap.py` (verbatim in bead `conveyer-hpp.13.10`'s design field) and the OQ-6 stats probe (bead `conveyer-hpp.13.11`) — are committed by the build epic under `spine/tests/probes/` as evidence-preserving artifacts (§16): a probe *establishes* an engine behavior once on the pinned stack; the harness cases above *defend* it from then on. §8.2's rendering differential (comparison rendering ≡ reference semantics, nulls included) lands beside them (§13).

## 12. Observability

**The value-free law is this section's admission rule** ([S-7]/[S-18], restated): every channel below carries **enum codes, counts, and lineage identifiers only** (batch/attempt/snapshot ids, table names) — never payload-derived values. `record_key` is itself [DS-1]-classified, so no metric dimension, log line, or ledger projection ever carries a key — the divergent-duplicate channel **counts keys, never names them** (a key in a CloudWatch dimension would leak the pseudonymous identifier into a surface the lake's IAM never governed).

- **Ledger (attempt-truth; L-4 additive-only).** The per-table maps are **errata item 20's** (`facts_appended_by_table` / `snapshot_ids_by_table` / `rows_merged_by_table`, singular columns as totals / one-snapshot forms) — cited, never restated; §4.2's `BatchContext` fields are their field-level ground. Commit rows additionally project the **delta predecessor recordings**: `delta_predecessor_batch_ids`, `delta_read_snapshot_ids`, and `delta_probe_refusal` (§4.2's set-once slots) — resolution provenance as data; L-1 untouched (observability, never control). **Rebuild attempts ride the ledger as their own rows** — the rebuild stage-vocabulary accretion registered to 004.1 (§16); until it lands, the EMF metric below is the retry record, named as the interim.
- **EMF metrics (new at this revision; all reason/lineage-dimensioned, all value-free):**
  - **`DeltaProbeRefusals`** — F-5's obligation, discharged at §7.2: reason-dimensioned (the four codes, verbatim), emitted at commit's effect point when resolution refuses. Alarm shape: a **persistent nonzero rate on one feed** — safe but symptomatic (the §8.3 race, a marker-write bug, or a misbehaving field). **Deliberately no probe metric for the read-1 coherence-clause keeps** (§7.2 paths 2/3) [AE2-10]: they are not probe refusals (`delta_probe_refusal` stays null). Their persistent form — a permanently wedged same-feed batch forcing everything-novel on every successor — surfaces through the **failed-execution alarm** on the wedged batch's own attempts plus the successors' ledger rows carrying **empty `delta_predecessor_batch_ids`**: the stated channel for the "never uninspectable keeps" dual on these paths.
  - **`DivergentDuplicates`** — D-2(b)'s observable-data condition made a number: per (batch, fact table), the count of `record_key`s carrying >1 distinct `content_hash` within the batch (both committed, by design); dimensioned by fact table; emitted at commit after the within-batch collapse (§8.2's reduce adjudicates them by hash tiebreak). Symptomatic, never blocking: a sustained rise means an upstream determinism or feed-quality problem — the metric is the page, the facts are the evidence.
  - **`RebuildSwapRetries`** — RB-2's attempt-truth at metric grain: consecutive refused swaps within one rebuild run, dimensioned by pipeline and state table. The **alarm threshold is 008's register row** (RB-3, §16), priced under the replace shape — each losing attempt is one full recompute plus one refused commit plus orphaned files — and **re-derived if the swap-as-MERGE fallback is ever adopted** (the ADR's fallback clause: different write-amplification economics).
- **No-op visibility, per table.** Fold's logical no-ops are stated, never silent: `rows_merged_by_table[t] = 0` with the key absent from `fold_snapshot_ids` / `snapshot_ids_by_table` (§8.2's projection rule over errata #9's signal) — a rerun that no-ops everywhere is legible from the maps alone.
- **Athena.** No new named query at this revision: refusal reasons, per-table maps, and delta recordings are ledger columns served by the existing runs queries; the marker table is directly queryable for batch-truth under its own posture (§6.3). If refusal triage grows a standing need, a `spine-delta-refusals-30d` query is an 008-register candidate, not a Phase-1 surface.
