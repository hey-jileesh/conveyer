# Data Ingestion Module — Low-Level Design (Phase 1)

**Status:** v1.1 (v1.1: implementation idiom revised to functional/data-oriented Python — §7.0, D-17) · **Implements:** *Data Ingestion Module — Architecture Description* (Draft v0.1) · **Parent:** *Large-Volume Batch Data Processing* · **Stack:** Python 3.12 + Terraform (AWS provider ≥ 5.60) · **Scope:** Phase 1 slice — delivery ledger, registration, `s3-push` driver, `sftp-pull` driver, absence detection

> **How to use this document (implementing agent, read first).**
> This is a build spec, not a discussion. Every schema, signature, resource, and algorithm here is normative. Implement in the milestone order of §13; each milestone has acceptance criteria expressed as `make` targets that must pass. Where behavior is not specified, do the simplest thing consistent with the invariants in §14 — do not add capabilities, hooks, options, or "improvements" beyond this spec. If a genuine contradiction or gap blocks you, stop and surface it rather than inventing.
>
> The entire acceptance loop for Python code runs locally (no AWS account needed): the ledger uses an injectable Iceberg catalog (SQLite locally, Glue in prod), the CAS store and event bus are exercised under `moto`, and SFTP is an in-memory record of functions. Terraform is validated with `terraform validate` + `terraform plan` against a real account only at deploy time.

## 1. Purpose, Scope, Non-Goals

This document specifies the concrete implementation of the ingestion module's Phase 1 slice, per the architecture description's own sequencing (§13 there, steps 1–3):

**In scope (build all of this):**

1. The **delivery ledger** — an append-only Iceberg table plus the pure fold functions over it (dispositions, watermarks).
2. **Registration** — the shared library that verifies completeness, mints identity, arbitrates duplicate races via a CAS turnstile, appends ledger rows, and emits `delivery-registered`.
3. The **`s3-push` driver** — partner drops objects into an `incoming/` vestibule prefix; an event-triggered registrar performs the canonical move and registration.
4. The **`sftp-pull` driver** — scheduled pull from a remote SFTP endpoint, streaming to the landing zone with hash-as-you-go, then registration through the same shared library.
5. **Absence detection** — scheduled comparison of ledger vs. per-feed expectation schedules, emitting `delivery-overdue`, plus a stuck-claim sweep.
6. **Terraform** for everything above, greenfield and self-contained: only names/region/tags as inputs.
7. **Two exemplar source plugins** (`carrier-x/commission-statements` over sftp-pull, `carrier-y/renewal-statements` over s3-push) with full fixture suites.

**Out of scope (do not build):**

- The stage sequence (`land → … → publish`) and Step Functions state machines. The module's boundary is exactly the three outputs: canonical landing objects, ledger rows, `delivery-registered` events. Phase 1 wires events to a CloudWatch log group so they are observable; per-feed Step Functions targets arrive with the parent module.
- `api-pull` and `db-unload` drivers. The driver interface (§7.6) is written so they slot in later; leave stubs raising `NotImplementedError` with a comment pointing here.
- Quarantine, `pre_check`, schema/quality validation of *content*. Registration checks completeness, never content.
- Lake Formation integration (see D-9 in §2).
- Partner-custom manifest formats (the pure-function hook is defined in §6.3 but no implementation is required in Phase 1).

## 2. Decision Record

Decisions the architecture description left open, now pinned. **D-2, D-3, D-5, D-8, D-9 are conscious refinements of (or narrowings from) the architecture doc** — each names what it trades.

| # | Decision | Choice | Rationale / trade-off |
|---|---|---|---|
| D-1 | CAS turnstile store | **DynamoDB, conditional writes**, single table, TTL cleanup | Long-standardized `attribute_not_exists` semantics; TTL expires markers with zero information loss (the ledger remembers, the pointer only coordinates); item carries claim state for crash takeover (§8.4). S3 `If-None-Match` rejected: no conditional *update* for takeover, no TTL. |
| D-2 | Compute runtime | **One Lambda container image for all components** (registrar, per-feed sftp-pull driver instances, absence, maintenance), CMD overridden per function. *Deviates from the arch doc's "Glue Python jobs" mapping for pull drivers.* | One packaging path, one Terraform pattern, Python 3.12 everywhere, sub-second cold path for event-triggered registration. Cost: 15-min/10 GB-ephemeral Lambda ceiling on a single driver run — mitigated by streaming (no local spool), a per-run acquisition budget with carry-over (§9.2), and a named promotion path: the driver contract is runtime-agnostic, so a feed whose transfers outgrow Lambda moves to a Glue/Fargate runner by config, not redesign. At statement-file volumes the ceiling is nowhere near. |
| D-3 | `s3-push` landing flow | Partner writes to `<source>/<feed>/incoming/` (the **vestibule**); the registrar verifies, then **copies** to the canonical `received_at=` prefix and registers. Vestibule objects expire by lifecycle (14 d), never deleted by code. | Partners cannot mint received-at prefixes, and re-sends of the same filename must not be denied. The alternative — register objects where the partner wrote them, disambiguated by S3 versionId — complects object identity with S3 versioning mechanics and puts version-qualified URIs in every ledger row. The copy is a *move* (byte-verbatim, server-side), not a transform; "no acquisition code" for s3-push becomes "no *transport* code," which is the claim that mattered. |
| D-4 | Batch-id minting | **`batch_id = UUIDv5(CONVEYER_NS, feed_id + "\n" + content_hash)` in all modes**, including manifest feeds. | One rule, one code path. The arch doc permits `f(feed_id, manifest_id)` for manifest feeds as an alternative; that is a future optimization for deliveries too large to hash (none exist in Phase 1). Consequence: a partner re-sending identical bytes under a fresh manifest id dedups as `duplicate` — the desired behavior. |
| D-5 | Trailer completeness semantics | Trailer mode = **tail-assertion check**: the delivery's final line must match the feed's declared trailer regex; the asserted record count is *recorded* in the ledger (`asserted_record_count`) for `pre_check` to verify at row level. Registration never counts rows. | Keeps the no-interpretation rule maximal while making trailer completeness real (a truncated file lacks its trailer → `incomplete`). Reading a bounded tail (ranged GET, 4 KiB) is the completeness assertion itself, framework-owned, never mutating. Phase 1 constraint: trailer mode ⇒ single-data-object deliveries. |
| D-6 | Content-hash canonicalization (arch open item 3) | §6.5. Per-object SHA-256 over raw bytes; delivery hash = SHA-256 over a sorted `sha256sum`-style listing of data objects, **manifest excluded**. | Deterministic across received-at prefixes and manifest regeneration; uniform for 1..N objects. |
| D-7 | Ledger write path | **pyiceberg** with an **injectable catalog**: `GlueCatalog` in prod, `SqlCatalog` (SQLite + local FS warehouse) in tests. App-level retry on commit conflicts. Table maintenance (compaction, snapshot expiry) via scheduled **Athena** `OPTIMIZE`/`VACUUM`. | The catalog is a parameterized dependency, so the full acceptance loop runs without AWS. Athena also gives operators a query surface over the ledger (named queries, §11.4). Trade-off: Athena workgroup + results bucket exist solely for maintenance/ops queries — cheap, and framework-owned. |
| D-8 | Per-feed ledger isolation | **Partial.** Landing prefixes and secrets are isolated per feed by IAM (structural). Ledger writes are table-scoped: Iceberg's shared metadata tree cannot be partition-scoped by IAM. | The arch doc's "its own ledger partition" is achievable for data-file prefixes but not metadata commits in a single Iceberg table. Per-feed ledger *tables* rejected: fragments every operational query. Accepted because drivers are framework-owned code (plugins contribute no effectful code at all), so the ledger's writer set is the platform, not the plugin author. Named, not hidden. |
| D-9 | Governance | IAM + bucket policies only in Phase 1; **Lake Formation deferred** to integration with the parent lane's lakehouse. | Greenfield-self-contained Terraform must not bootstrap an LF admin model. Append-only is still structural: no principal except maintenance holds `s3:DeleteObject` on lake/landing data (§10.6). |
| D-10 | Timer completeness | `s3-push` + timer: **rejected at config validation** in Phase 1 (needs delayed re-check machinery). `sftp-pull` + timer: supported as **remote-mtime quiet window** — a file is a candidate only when `now − mtime ≥ quiet_window_minutes`. | The pull variant is the honest SFTP form of a quiet window and costs nothing extra. The push variant would silently complect *when* with *correctness* in an event-driven path; deferring it is the reviewed trade-off the arch doc demands (`accepted_risk` is still a required field wherever timer appears). |
| D-11 | Expectation grammar | Small closed grammar: `daily \| weekdays \| weekly:<mon..sun> \| monthly:<1..28>` + `by: "HH:MM"` + IANA `timezone`. | Covers every Phase 1 feed; a cron-expression expectation is a Phase 2 additive extension. Small grammars stay foldable. |
| D-12 | Provisioning source of truth | **Terraform reads `sources/**/source.yaml` directly** (`fileset` + `yamldecode`) and instantiates one `feed` module per file; it also renders the merged **feed registry** (`feeds.json`) to S3 for the absence detector. No CDK, no codegen step. | "Merging source.yaml triggers IaC" with zero intermediate machinery. The registry the runtime reads is provably the config that provisioned the infrastructure. |
| D-13 | Secrets | Terraform creates the per-feed Secrets Manager secret *shell*; values are set out-of-band (`make put-secret`). Secret values never appear in Terraform state. Rotation: arch open item 2, out of scope. | Standard practice; documented in the runbook (§10.8). |
| D-14 | Event delivery semantics | **All module events are at-least-once**; `batch_id` is the consumer dedup key for `delivery-registered`, `(feed_id, expectation_date)` for `delivery-overdue`. (The parent lane's natural implementation: `states:StartExecution` with `name = batch_id` gives exactly-once executions for free.) | EventBridge is at-least-once regardless; pretending otherwise would be a lie in the contract. Stated in the event contract (§6.4). |
| D-15 | Partner access to the vestibule | s3-push feeds declare `connection.partner_principal_arns` (external AWS principals) in `source.yaml`; the platform's landing-bucket policy grants those principals `s3:PutObject` on that feed's `incoming/*` only. | Self-contained and per-feed-scoped; onboarding stays "merge source.yaml". Partners without an AWS principal (SFTP-style upload tooling) are a Phase 2 concern (Transfer Family → same vestibule, §16). |
| D-17 | Implementation idiom | **Functional, data-oriented Python (§7.0):** values (frozen dataclasses / pydantic at boundaries) + module-level functions; effects passed as **records of functions**; registration split into a **pure planner and a thin interpreter** (the effect plan is data); defects are **values, not exceptions** — the pure core never raises. **No FP frameworks** (`returns`, `toolz`, `pyrsistent`, `effect`, …): stdlib `functools`/`itertools`/comprehensions only. | Monadic result types and persistent collections buy little here — errors are already data (dispositions, `Defect` values) and collections are small — while costing every future reader and agent familiarity: the easy/simple trade, named in the direction Hickey warns about *and* the direction Python idiom demands. Enforced structurally by the purity linter (§12.2), not by convention. |
| D-16 | Pull-driver identical re-sends | A remote file whose `(name, bytes)` the ledger already accounts for is **skipped at selection — no ledger row** (indistinguishable from a file simply not yet expired remotely). *Narrows the arch §8 "ledger explains the skip" row for pull drivers.* The explaining `duplicate` row still exists wherever bytes are actually re-acquired: every s3-push replay, and pull re-pulls invoked with `force: true` (§7.6). | A pull driver cannot distinguish "partner re-sent identical file" from "file still sitting there"; recording a `duplicate` row per schedule tick would flood the ledger with non-events. Named, accepted. |

## 3. System Overview

### 3.1 Components and runtimes

| Component | Runtime | Trigger | Role (flow vocabulary) |
|---|---|---|---|
| **Registrar** | Lambda (container), framework-owned, one function | EventBridge rule on S3 `Object Created` under each s3-push feed's `incoming/` prefix (suffix-filtered per completeness mode) | *move* (vestibule → canonical) + *remember* |
| **sftp-pull driver** | Lambda (container), **one function instance per feed** (same image, `FEED_ID` env, per-feed IAM role) | EventBridge Scheduler cron (feed's declared schedule + timezone) | *move* (remote → canonical) + *remember* (via shared registration core) |
| **Absence detector** | Lambda (container), one function | EventBridge Scheduler, hourly | *remember*, negatively: ledger vs. expectations → `delivery-overdue`; plus stuck-claim sweep (§9.3) |
| **Maintenance** | Lambda (container), one function | EventBridge Scheduler, weekly | Athena `OPTIMIZE` + `VACUUM` on the ledger; the only principal with delete rights on lake data |
| **Delivery ledger** | Iceberg table `ingestion.delivery_ledger` on S3, Glue catalog | — | the reified process: the logbook |
| **CAS turnstile** | DynamoDB table | — | the tiny mutable pointer set: the turnstile |
| **Event bus** | EventBridge custom bus | — | *route*: `delivery-registered`, `delivery-overdue` |

One container image serves all four Lambda functions; the handler is selected by function-level `CMD` override (§7.1).

### 3.2 Flows

```
s3-push:
  partner PUT s3://<landing>/<source>/<feed>/incoming/<name>
    ─▶ S3→EventBridge "Object Created" (suffix-filtered) ─▶ Registrar λ
        1 read+verify (manifest/trailer) from incoming/
        2 hash objects (stream), mint batch_id
        3 CAS claim (turnstile)                 ── loser ─▶ ledger row: duplicate, stop
        4 copy incoming/* → received_at=…/dl-<delivery_id>/   (server-side, verbatim)
        5 ledger append: registered (+ superseded row for prior, if correction)
        6 emit delivery-registered ─▶ bus ─▶ [phase 2: per-feed Step Functions]

sftp-pull:
  Scheduler cron ─▶ driver λ (this feed's instance)
        1 fold ledger → acquired set (watermark-as-fold; no stored cursor)
        2 list remote, select candidates (pattern, quiet window, not-yet-acquired)
        3 per candidate: stream remote → canonical landing path, hashing en route
        4 registration core: mint → CAS → ledger → event   (same steps 3..6 as above)

absence (hourly):
  Scheduler ─▶ absence λ
        for each feed in registry with an expectation:
          deadline passed && no qualifying registered delivery && overdue-marker CAS wins
            ─▶ ledger-independent: emit delivery-overdue
        + stuck-claim sweep: CAS items in_progress > 20 min → re-invoke registrar
```

### 3.3 What never happens here (inherited invariants, enforced in §12/§14)

No parsing or transformation of data bytes (the bounded reads in D-5/§6.3 are completeness assertions, not interpretation); no writes to any table but the ledger; no mutable cursor files; no update-in-place anywhere — dispositions accrete as new rows; no code in `source.yaml`.

## 5. Naming, Identifiers, and Storage Layout

All physical names derive from two variables: `name_prefix` (default `conveyer`) and `env` (e.g. `dev`). `${p}` below means `${name_prefix}-${env}`.

| Thing | Name / format |
|---|---|
| Landing bucket | `${p}-landing` |
| Lake bucket (ledger data) | `${p}-lake` |
| Artifacts bucket (registry, Athena results) | `${p}-artifacts` |
| Vestibule prefix (s3-push only) | `s3://${p}-landing/<source>/<feed>/incoming/<partner-chosen-name>` |
| Canonical landing key | `s3://${p}-landing/<source>/<feed>/received_at=<YYYYMMDDTHHMMSSffffffZ>/dl-<delivery_id>/<original-name>` |
| Glue database | `${name_prefix}_${env}_ingestion` (underscores; Glue-safe) |
| Ledger table | `<glue db>.delivery_ledger` at `s3://${p}-lake/ledger/` |
| CAS table (DynamoDB) | `${p}-ingestion-cas`; pk (S): see §8.4 key formats |
| Event bus | `${p}-bus` |
| Lambda functions | `${p}-registrar`, `${p}-driver-<source>--<feed>` (slashes → `--`), `${p}-absence`, `${p}-maintenance` |
| ECR repo | `${p}-ingestion` |
| DLQ (SQS) | `${p}-ingestion-dlq` |
| Feed registry object | `s3://${p}-artifacts/registry/feeds.json` |
| `feed_id` | `<source>/<feed>`, both segments `^[a-z0-9][a-z0-9-]*$` |
| `delivery_id` | UUIDv4, minted by the effect side (`effects/ids.py`) at the start of acquisition/registration |
| `batch_id` | UUIDv5 per §6.6 |
| `content_hash` | `sha256:<64 lowercase hex>` per §6.5 |
| `driver_run_id` | the Lambda request id (`context.aws_request_id`) |
| Event `source` field | `conveyer.ingestion` |

Canonical-key timestamp is `received_at` = the **acquisition-start instant** (UTC, microseconds, basic format): minted by `clock.now()` before the first byte moves (registration start for s3-push, stream start for sftp-pull), so the canonical prefix is known — and stable across crash recovery — before any write. The `dl-<delivery_id>` path segment makes canonical keys collision-free by construction — the deny-overwrite story does not depend on timestamp granularity.

## 6. Contracts and Data Model

All contracts are **pydantic v2 models in `ingestion/core/model.py`** — the single source of truth. `make schemas` exports them as JSON Schema into `contracts/` (via `model_json_schema()`); CI fails if the exported files differ from what is committed (drift check). Schema evolution is additive-only; a breaking change is a new versioned model + new file.

### 6.1 `source.yaml` — `FeedConfig`

```python
class SftpConnection(BaseModel):
    model_config = ConfigDict(extra="forbid")
    secret_ref: str                      # full Secrets Manager ARN, validated by regex
    remote_path: str                     # absolute remote dir, e.g. /outbound/commissions/
    file_pattern: str = "*"              # fnmatch glob applied to remote basenames

class S3PushConnection(BaseModel):
    model_config = ConfigDict(extra="forbid")
    partner_principal_arns: list[str] = Field(min_length=1)   # external AWS principals granted
                                                              # PutObject on this feed's incoming/ (D-15)

class Trigger(BaseModel):
    model_config = ConfigDict(extra="forbid")
    schedule: str                        # 6-field EventBridge cron, e.g. "cron(0 13 ? * MON-FRI *)"
    timezone: str = "UTC"                # IANA name; validated via zoneinfo

class Expectation(BaseModel):
    model_config = ConfigDict(extra="forbid")
    expected: str                        # "daily" | "weekdays" | "weekly:mon".."weekly:sun"
                                         # | "monthly:1".."monthly:28"   (D-11)
    by: str                              # "HH:MM" 24h
    timezone: str                        # IANA name

class TrailerSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")
    pattern: str                         # Python regex the final non-empty line must fully match
    count_group: str | None = None       # named group holding the asserted record count

class TimerSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")
    quiet_window_minutes: int = Field(ge=1, le=1440)
    accepted_risk: str = Field(min_length=20)   # forced prose; reviewed in PR

class Completeness(BaseModel):
    model_config = ConfigDict(extra="forbid")
    mode: Literal["manifest", "trailer", "timer"]
    manifest_pattern: str = "*.manifest.json"   # used iff mode == manifest
    trailer: TrailerSpec | None = None          # required iff mode == trailer
    timer: TimerSpec | None = None              # required iff mode == timer

class FeedConfig(BaseModel):
    model_config = ConfigDict(extra="forbid")
    feed_id: str                         # ^[a-z0-9][a-z0-9-]*/[a-z0-9][a-z0-9-]*$
    driver: Literal["s3-push", "sftp-pull", "api-pull", "db-unload"]
    pipeline: str                        # stage-sequence package ref; opaque string here
    connection: SftpConnection | S3PushConnection | None = None
                                                # SftpConnection required iff sftp-pull;
                                                # S3PushConnection required iff s3-push (D-15)
    trigger: Trigger | None = None              # required iff pull driver
    expectation: Expectation | None = None
    completeness: Completeness
    format_hints: dict[str, JsonValue] = {}     # recorded into registry verbatim; the
                                                # ingestion runtime NEVER interprets these
```

Cross-field validation (`@model_validator`), each violation a distinct error message:
`sftp-pull` requires `SftpConnection` + `trigger`; `s3-push` requires `S3PushConnection` and forbids `trigger`; `mode==trailer` requires `trailer`; `mode==timer` requires `timer`; `manifest_pattern` must be `*<literal-suffix>` (leading `*`, no other wildcards — the EventBridge suffix rule in §10.7 depends on it); **`s3-push` + `mode==timer` → hard error `"timer completeness is not supported for s3-push in Phase 1 (LLD D-10)"`**; `api-pull`/`db-unload` → hard error `"driver not implemented in Phase 1"`. The same model validates in three places: unit tests, `make registry` (local render), and implicitly at `terraform plan` time (Terraform only checks YAML well-formedness; the authoritative validation gate is CI running `make registry` — see §12.6).

Partition spec: `identity(feed_id)`, `day(received_at)`. Write mode defaults; no sort order.

**Column population by disposition** (normative — no other combinations exist):

| Disposition | `batch_id`/`content_hash`/`size_bytes` | `objects` | `object_uris` |
|---|---|---|---|
| `registered`, `superseded` (accretion), pull-side `duplicate` | populated | all objects, canonical `uri`s, `sha256` set | canonical data URIs |
| s3-push `duplicate` (loser never copies) | populated (hashed pre-claim) | vestibule `uri`s, `sha256` set | vestibule URIs (transient — vestibule expires in 14 d; the winner's `registered` row holds the permanent URIs) |
| `incomplete` | null (never fully hashed) | observed inventory: names + bytes; `uri`/`sha256` null except objects already streamed | `[]` |
| `unreadable` | populated if hashing completed before the defect surfaced, else null | as observed at failure | `[]` |

**Append-only discipline, restated as implementation rules:** the only ledger write function in the codebase is `fx.ledger.append(rows)`; there is no update/delete anywhere. A disposition change (e.g., supersession) is a **new row** with the same `delivery_id`, new `recorded_at`, new `disposition`, and the original row's identity columns copied verbatim. Crash-recovery replays may append byte-identical duplicate rows; the latest-disposition fold (§7.4) makes them harmless. Ledger readers must always fold, never read raw rows as current state.

### 6.5 Content-hash canonicalization (normative algorithm, D-6)

```
inputs:  data objects only (manifest object EXCLUDED), each with
         (name = original basename, sha256_hex = SHA-256 of raw bytes)
steps:
  1. lines = [f"{sha256_hex}  {name}" for each object]      # two spaces, sha256sum style
  2. lines.sort()                                            # bytewise lexicographic
  3. digest = SHA256("\n".join(lines).encode("utf-8"))
  4. content_hash = "sha256:" + digest.hexdigest()
```

Properties: independent of received-at prefixes, upload order, and manifest regeneration; uniform for single- and multi-object deliveries; a renamed-but-identical file is a *different* delivery (names participate — a deliberate choice: the partner's naming is part of what was asserted). Implemented as `core.hashing.canonical_content_hash(objects: Sequence[tuple[str, str]]) -> str`; property-tested (§12.3).

## 7. Python Implementation Spec

### 7.0 Implementation idiom (normative — D-17)

The codebase is **functional and data-oriented**: it contains exactly two kinds of things, **values** and **functions**. This is not a style preference; each rule below removes a specific complection, and each is machine-enforced by the purity linter (§12.2).

1. **Values.** Immutable data only: `@dataclass(frozen=True)` for internal values, pydantic `BaseModel` for boundary contracts (parse, don't validate-in-place), `enum.Enum` for closed vocabularies. **No other `class` statements exist anywhere in `ingestion/`** — no service classes, no inheritance (beyond `BaseModel`/`Enum` bases), no methods carrying logic. A class with methods and state complects state⟷identity⟷behavior; a frozen dataclass is just a named value.
2. **Functions.** All logic is module-level functions: pure ones in `core/`, effectful ones in `effects/` and the thin orchestration modules. Derived values come from functions over values (`folds.feed_watermark(rows)`), never from methods on the data.
3. **Effects are records of functions.** A capability is a frozen dataclass whose fields are `Callable`s (§7.7) — the Python spelling of a Clojure map of fns. Production records are built by `make_*_fx` factories whose closures capture boto3/pyiceberg clients; test records are built from plain local functions (no mocking framework, ever). Swapping the world under the code is constructor substitution, not patching.
4. **Defects are values; the pure core never raises.** Completeness evaluators return a `verdict`; manifest parsing returns `ManifestV1 | Defect` (§7.3). `raise`/`try` are banned from `core/` by the linter. Exceptions remain only at effect boundaries, where they are Python-idiomatic: `TransientError` for infra failures that should retry/alarm.
5. **Decide, then do.** Anything that must both compute *what to do* and *do it* is split into a pure planner returning a plan-as-data and a tiny interpreter that walks the plan (§8). Golden tests assert on plans without executing anything; the interpreter is small enough to verify by reading.
6. **Stdlib FP only.** `functools`, `itertools`, comprehensions, generators. No `toolz`/`returns`/`pyrsistent`/`effect`-style frameworks, no point-free pipelines, no decorator magic. Plain `def`, explicit intermediate names. Unfamiliar constructs cost every future reader more than they buy this codebase (small collections, errors already modeled as data).

## 8. Registration — the Shared Core

Registration is split per §7.0 rule 5 — **pure planners in `core/decisions.py`, a thin interpreter in `registration/registrar.py`**. The planners decide everything (which rows, which copies, which event, whether to complete the claim) and return it as a value; the interpreter walks that value in a fixed order. Every row ever appended to the ledger is built by a pure function and visible in a plan.

`registration/registrar.py` exports exactly three functions, the only code in the module (and, with §9.4's reconciliation append, the only code anywhere) that performs ledger/event effects:

- `register_delivery(req: RegistrationRequest, fx: Effects) -> DeliveryOutcome` — the turnstile path, for complete verified deliveries: `claim → plan_registration → execute`.
- `record_nondelivery(feed, delivery_key, disposition, observed, notes, fx) -> DeliveryOutcome` — the non-turnstile path for `incomplete`/`unreadable` verdicts: `plan_nondelivery → execute`. The **append-on-change rule lives in the planner** (pure, testable): given the feed's prior rows, if the latest row for this `delivery_key` already has the same disposition *and* the same observed `(name, bytes)` inventory, the plan contains no rows (log DEBUG). This is what keeps a stuck incomplete manifest — re-examined every scheduled run and on every duplicate S3 event — from writing a row per run.
- `execute(plan: RegistrationPlan, fx: Effects) -> DeliveryOutcome` — the interpreter (§8.5).

The golden suite asserts the ownership rule by grepping call sites of `ledger.append` / `emit` (cheap, honest).

### 8.1 `RegistrationRequest`

```python
@dataclass(frozen=True)
class StagedObject:
    name: str                          # original basename
    role: Literal["data", "manifest"]
    uri: str                           # CANONICAL target URI (computed from received_at +
                                       #   delivery_id; the object may not exist there YET)
    bytes: int; sha256: str
    src_key: str | None                # s3-push: vestibule key to copy from in step D2;
                                       # sftp-pull: None (already streamed to `uri`)
@dataclass(frozen=True)
class RegistrationRequest:
    feed: FeedConfig
    delivery_id: str                   # minted by the caller (effects/ids.py)
    delivery_key: str                  # manifest_id | single data object basename
    received_at: datetime              # acquisition start (§5); fixes the canonical prefix
    driver: str; driver_run_id: str
    completeness: CompletenessResult   # already evaluated by the caller (complete=True)
    objects: list[StagedObject]        # data objects AND the manifest (role distinguishes)
```

Callers reach this point only with a *complete, verified, fully hashed* delivery: content is hashed **before** the turnstile in both drivers (from the vestibule for s3-push; while streaming to canonical keys for sftp-pull). Whether bytes already sit at canonical keys differs by driver and is captured per object in `src_key`. Incomplete/unreadable outcomes go through `record_nondelivery` and never enter the turnstile — this keeps `register_delivery` linear.

### 8.2 s3-push path (`drivers/s3_push.py` + `entrypoints/registrar_s3.py`)

Trigger: EventBridge "Object Created" (see §10.7 for the rule pattern). Steps:

1. Parse bucket/key from the event; derive `feed_id` from the key's first two segments; load `FeedConfig` from the registry. Key not under any feed's `incoming/` → log ERROR, return (misroute; the rule pattern should make this impossible).
2. **Manifest mode** (rule fires only on `manifest_pattern`-suffixed keys): `fx.store.get_bytes` the manifest (max 1 MiB) → `core.completeness.parse_manifest` (`Defect` → `record_nondelivery(unreadable)`, done — `delivery_key` falls back to the manifest basename). `list_prefix` the vestibule; for each manifest-declared file present: `stream_sha256` from the vestibule; then `evaluate_manifest`. Incomplete → **`record_nondelivery(incomplete)` + stop** (no retry: the partner uploads manifest last, so a manifest-first race is itself a partner defect; parts arriving later are followed by a re-sent manifest → new event → clean pass. The append-on-change rule absorbs duplicate events meanwhile; the absence schedule catches a never-completed delivery).
   **Trailer mode** (rule fires on every `incoming/` object): single object = the delivery. `stream_sha256` + `get_tail` → `evaluate_trailer`.
3. Mint: `received_at = clock.now()`; `delivery_id = new_delivery_id()`; `content_hash = canonical_content_hash(...)` (data objects only); `batch_id = mint_batch_id(...)`. Build `StagedObject`s: canonical target `uri`s under `received_at=<ts>/dl-<delivery_id>/`, `src_key` = each vestibule key. **No canonical write happens in this step.**
4. Build `RegistrationRequest`; call `register_delivery` (§8.3–8.5). The vestibule→canonical copy is step D2 *inside* the state walk — after the claim — so a duplicate-race loser never copies. Vestibule objects are always left in place (lifecycle expires them, D-3).

Plan content by `claim.kind` (all row values built here, per the §6.2 population table):

| `claim.kind` | Plan |
|---|---|
| `WON` | `rows` = registered row (+ `superseded` accretion row when a correction is detected: latest *registered* prior delivery — fold of `prior` — with same `delivery_key`, different `content_hash`); `copies` = one per `StagedObject` with `src_key` set; `event` set; `complete_claim` set |
| `LOST_COMPLETED` | `rows` = one `duplicate` row (this run's `delivery_id`, same `batch_id`); nothing else. Both sides of every race are remembered |
| `LOST_IN_PROGRESS` | Same as `LOST_COMPLETED`. A live concurrent owner is registering the content; this run's *observation* of it is still a fact, and "never a silent skip" (arch §2) admits no quiet exit. If the owner later crashes, the sweep resumes *its* claim; the duplicate row stands either way |
| `TAKEN_OVER` | As `WON`, but every row/copy/event is built from the **dead run's identity** in `claim.item` (`delivery_id`, `received_at`, canonical prefix, objects inventory — §8.4), so the plan is byte-identical to the one the dead run would have executed. Supersession detection runs here too (a takeover of a correction must not lose the supersession) |

Because plans are values, the planner is golden-tested exhaustively with zero infrastructure: G-03/04/06/11 first assert the *plan* (exact rows, copies, event), then run the interpreter against the local stack to assert the world agrees.

**Concurrent-correction race, named:** two *different* contents with the same `delivery_key` registering simultaneously hold different `batch_id`s, so the turnstile does not serialize them; both scan the ledger before either commit lands, and both may compute `supersedes = None`. Correctness is unharmed — the parent lane's delta detection makes the older batch's replayed facts no-ops (arch open item 4, default resolution), and "current delivery per `delivery_key`" is a fold (latest `received_at` wins). The missing `superseded` accretion row is repaired by the weekly reconciliation sweep (§9.4). Serializing registration per `delivery_key` was rejected: a second lock complects the turnstile's one job for a row the fold can derive.

### 8.4 The turnstile — `effects/cas.py`

DynamoDB `${p}-ingestion-cas`, on-demand billing, TTL attribute `expires_at`. Key formats (single table; per-feed IAM scoping via `dynamodb:LeadingKeys` `StringLike`, §10.7):

| pk (S) | Written by | Meaning |
|---|---|---|
| `batch#<feed_id>#<batch_id>` | registrar / drivers | Batch claim item |
| `overdue#<feed_id>#<expectation_date>` | absence detector | Overdue-emitted marker (dedup of `delivery-overdue`) |

Batch claim item attributes — everything a takeover needs to finish the registration **without re-deriving anything**: `feed_id`, `batch_id`, `delivery_id`, `driver` (`s3-push` | `sftp-pull` — the sweep routes on this, §9.3), `received_at` (ISO; fixes the canonical prefix), `delivery_key`, `content_hash`, `size_bytes`, `objects_inventory` (JSON: the `StagedObject` list — names, roles, canonical uris, bytes, sha256s, src_keys; bounded by the 1000-file cap, §6.3), `asserted_record_count`, `completeness_mode`, `trigger` (JSON: s3-push → the triggering vestibule key; pull → the window), `owner_run_id`, `status` (`in_progress` | `completed`), `claimed_at` (epoch s), `completed_at`, `expires_at` (= completion + 30 d, or claim + 30 d).

Result types are **plain frozen dataclasses in `core/model.py`** (pure data — `effects/cas.py` constructs them, `core/decisions.py` consumes them; effects import core, never the reverse):

```python
@dataclass(frozen=True)
class ClaimItem:      # mirror of the DynamoDB item above, typed
    feed_id: str; batch_id: str; delivery_id: str; driver: str

    objects_inventory: tuple[StagedObject, ...]; asserted_record_count: int | None
    completeness_mode: str; trigger: dict; owner_run_id: str
    status: str; claimed_at: int; completed_at: int | None
@dataclass(frozen=True)
class ClaimResult:
    kind: Literal["WON", "LOST_COMPLETED", "LOST_IN_PROGRESS", "TAKEN_OVER"]
    item: ClaimItem | None            # None iff WON (this run's request IS the item);
                                      # on TAKEN_OVER, the DEAD run's item — the identity to adopt
```

`effects/cas.py :: make_cas_fx(dynamodb_client, table) -> CasFx` (record shape in §7.7). Function semantics:

```
claim(req, batch_id, run_id, trigger, now) -> ClaimResult:
    PutItem (full item built from req) ConditionExpression attribute_not_exists(pk) → WON
    else GetItem (consistent read):
      status == completed                                  → LOST_COMPLETED(item)
      status == in_progress and now - claimed_at <= 1200 s → LOST_IN_PROGRESS(item)
      status == in_progress and stale:
        UpdateItem SET owner_run_id = run_id, claimed_at = now
          ConditionExpression owner_run_id = <observed> AND status = "in_progress"
                                                         → TAKEN_OVER(item)
        condition failed (someone else took it)           → LOST_IN_PROGRESS(item)
complete(feed_id, batch_id, run_id, now):
    UpdateItem SET status="completed", completed_at, expires_at
      ConditionExpression owner_run_id = run_id   (fencing: a taken-over zombie cannot
      complete; its late writes are harmless duplicates by design)
sweep_stale(now) -> list[ClaimItem]      # absence λ; Scan w/ filter — table is tiny
marker_exists(pk) -> bool                # overdue markers (§9.3)
mark(pk, now, ttl_days=35) -> bool       # conditional put; True iff first writer
```

Staleness threshold 1200 s > max Lambda duration (900 s): a stale `in_progress` claim provably has no live owner.

### 8.5 `register_delivery` — normative state walk

```
register_delivery(req, fx):
  A. claim = fx.cas.claim(req, batch_id, run_id, trigger, fx.now())
          # s3-push: BEFORE any canonical write. sftp-pull: after streaming (§9.2 note).
  B. plan  = plan_registration(claim, fx.ledger.scan_feed(feed_id), req, fx.now())
          # PURE. On TAKEN_OVER the plan is rebuilt from claim.item — NOTHING re-derived,
          # so every key/row below is identical to what the dead run would have written.
  C. return execute(plan, fx)

execute(plan, fx):                        # the interpreter — fixed order, no judgment
  E1. for c in plan.copies: fx.store.copy_verbatim(c)
          # s3-push move; idempotent — fixed canonical keys from received_at + delivery_id;
          # a recovery re-copy writes identical bytes (versioning absorbs it; the one
          # sanctioned "overwrite", identical by construction).
          # (sftp TAKEN_OVER: objects already streamed to claim.item's uris pre-claim;
          #  plan.copies == () → E1 is a no-op.)
  E2. if plan.rows:  fx.ledger.append(plan.rows)      # one commit — registered row and any
                                                      #   superseded accretion row land atomically
  E3. if plan.event: fx.emit("delivery-registered", plan.event)
  E4. if plan.complete_claim: fx.cas.complete(...)
  E5. metrics; return plan.outcome

Crash matrix: die before A → event redelivery / next schedule re-runs everything (no trace,
  except sftp's already-streamed canonical objects, which the resumed run reuses).
  Die A..E4 → claim stale after 20 min → sweep re-invokes (§9.3) → TAKEN_OVER plan re-executes
  E1–E5 against the claim item's fixed identity; every step is idempotent (fixed keys;
  append+fold; at-least-once event; conditional complete). Duplicate ledger rows / events
  from replays are absorbed by folds and batch_id dedup (D-14).
```

`register_delivery` and `execute` together are ~50 lines; all judgment lives in `plan_registration`. Keep it that way — a conditional appearing in the interpreter beyond the four `if plan.x` guards is the design eroding.

## 9. Drivers, Absence, Maintenance

### 9.1 s3-push — already fully specified by §8.2 + §8.5. No other code exists for it.

### 9.2 sftp-pull — `drivers/sftp_pull.py`

Entry: Scheduler (payload `{}`) or operator invoke (`{"window": …, "force": bool}`) or sweep resume (`{"resume_batch_id": …}`, §9.3) → per-feed function → `acquire(feed, window, fx)`:

```
0. resume_batch_id present → load claim item; verify claim.item.objects_inventory all
   present at their canonical uris (list) → rebuild RegistrationRequest from the item →
   register_delivery (enters at claim(); gets TAKEN_OVER; resumes D3–D5). Done.
1. rows      = fx.ledger.scan_feed(feed_id, since = now - lookback)    # lookback var, default 45 d
   acquired  = core.folds.acquired_final(rows)
   defective = core.folds.observed_defective(rows)
2. sftp      = fx.sftp_fx_for(feed.connection.secret_ref)              # connect happens here
3. listing   = sftp.listdir(feed.connection.remote_path)
   if window.start/end given: filter listing to mtime ∈ window          # operator re-pull
4. mode == manifest:
     for m in core.windows.select_manifests(listing, acquired, pattern, force):
       # non-final manifests re-examined every run by design (§7.4)
       read remote manifest (≤1 MiB) → ManifestV1
         parse failure → record_nondelivery(unreadable, key=m.name)     # append-on-change dedups
       parts all present in listing with matching bytes?
         no  → record_nondelivery(incomplete, key=manifest_id, observed=listing∩manifest)
       yes → mint received_at + delivery_id; stream each part AND the manifest:
             fx.store.stream_upload(sftp.read_chunks(path), canonical key) — hashed en route
             streamed sha256 != manifest sha256 → record_nondelivery(unreadable) & abandon
             evaluate_manifest → RegistrationRequest (src_key=None) → register_delivery
   mode == trailer | timer:
     for f in core.windows.select_candidates(listing, acquired, defective, pattern,
                                             completeness, now, force):
       mint received_at + delivery_id; stream to canonical (hash en route)
       trailer: fx.store.get_tail on the STREAMED object → evaluate_trailer
                verdict incomplete/defective → record_nondelivery(...)  # observed_defective
                                                                        #   suppresses re-pulls
       timer:   complete by selection (quiet window)
       → register_delivery
5. Budget: stop starting new deliveries once elapsed > 10 min or bytes > budget var
   (default 5 GiB); log carry-over count + metric DriverCarryOver. Next scheduled run
   (or an operator invoke) continues — safe because every step is idempotent.
```

**Ordering note (differs from s3-push, deliberately):** the pull driver streams to *canonical* keys **before** claiming the turnstile, because the content hash — hence `batch_id` — is only known after the bytes have moved. A duplicate (`force` re-pull, or a defective-then-fixed file whose content matches an already-registered delivery) therefore leaves an orphaned canonical prefix (`dl-<loser delivery_id>/`) that no `registered` row references. Harmless: append-only zone, the ledger is the index, and the `duplicate` row's `objects` column documents the loser's URIs. Scheduled-path re-pulls of already-acquired files are pre-filtered by the `acquired_final` ∪ `observed_defective` folds — which, because `objects` includes the manifest (§6.2), covers manifests, parts, and single-file deliveries alike.

Failure isolation: exceptions per delivery are caught at the loop boundary — one bad delivery never blocks the rest of the window. `TransientError`s are re-raised **after** the loop completes (so the run is marked failed and alarmed) if any delivery failed transiently.

### 9.3 Absence detector — `absence/detector.py`

Hourly. For each registry feed with an `expectation`: `overdue = core.expectations.overdue_dates(exp, [r.received_at for r in registered_deliveries(scan_feed(feed, since=now-5d))], now)`; for each date, **emit-then-mark**:

```
pk = f"overdue#{feed_id}#{date}"
if not fx.cas.marker_exists(pk):
    fx.emit("delivery-overdue", ...); metric OverdueEmitted
    fx.cas.mark(pk)             # False (lost race) is fine — another sweep also emitted
```

At-least-once by construction (a crash between emit and mark re-emits next hour; consumers dedup on `(feed_id, expectation_date)`, D-14). Mark-then-emit was rejected: a crash after marking would lose the overdue signal *permanently* — an at-most-once operational loop is the one failure mode this component exists to prevent.

Then the **stuck-claim sweep**: `for item in fx.cas.sweep_stale(now):` route on `item.driver` — `s3-push` → async invoke `${p}-registrar` with a synthetic event built from `item.trigger`; `sftp-pull` → async invoke `${p}-driver-<slug(item.feed_id)>` with `{"resume_batch_id": item.batch_id}` (§9.2 step 0). Metric `StuckClaimsRecovered`; every sweep hit logs WARNING with the claim item.

### 9.4 Maintenance — `maintenance/optimize.py`

Weekly, three steps, each polled to completion (failure → raise → alarm):

1. `OPTIMIZE <db>.delivery_ledger REWRITE DATA USING BIN_PACK`.
2. `VACUUM <db>.delivery_ledger`. **Retention is governed by Athena's own table properties**, set at bootstrap: `vacuum_max_snapshot_age_seconds = 2592000` (30 d) and `vacuum_min_snapshots_to_keep = 5` — Athena VACUUM ignores the standard Iceberg `history.expire.*` properties, and its defaults (5 d) would silently shrink the audit window. `create_ledger.py` must set these explicitly.
3. **Supersession reconciliation** (§8.3's named race): query for `delivery_key`s with more than one live `registered` delivery (latest-disposition fold in SQL, as in the `current-dispositions` named query); for each, append `superseded` accretion rows for all but the newest `received_at`. Same shape as everything else: a pure planner in `core/decisions.py` (`plan_reconciliation(live_duplicates, now) -> tuple[DeliveryRecord, ...]`) and one `fx.ledger.append` here. Deterministic, idempotent (append-on-change). Metric `SupersessionsReconciled`.

This function's role is the **only** principal holding `s3:DeleteObject` on `${p}-lake/ledger/*` (D-9).

```json
  "detail": { "bucket": { "name": ["${p}-landing"] },
              "object": { "key": [ { "prefix": "<source>/<feed>/incoming/" } ] } } }
```
  For manifest mode add a suffix condition on the key: `{ "wildcard": "<source>/<feed>/incoming/*<manifest_pattern-suffix>" }` where the suffix is `manifest_pattern` with its leading `*` folded into the wildcard (Phase 1 constraint, validated in `FeedConfig`: `manifest_pattern` must be `*<literal-suffix>`). Trailer mode: prefix only.
- `aws_cloudwatch_event_target` → registrar Lambda + `aws_lambda_permission` (scoped to the rule ARN).

**sftp-pull feeds** (`sftp_pull.tf`):

- `aws_secretsmanager_secret` `${p}/sftp/<source>/<feed>` (shell only, D-13; `recovery_window_in_days = 7`).
- Per-feed **IAM role** `${p}-feed-<slug>`: landing `s3:PutObject/GetObject/ListBucket` **only** on `<source>/<feed>/received_at=*`; `secretsmanager:GetSecretValue` **only** on its own secret ARN; ledger-write + ledger-read (table-scoped, D-8); CAS `GetItem/PutItem/UpdateItem` with condition `dynamodb:LeadingKeys StringLike ["batch#<feed_id>#*"]`; `events:PutEvents`; registry read; DLQ send. *This is the blast-radius wall: the role cannot name another feed's prefix, secret, or CAS keyspace.*
- `aws_lambda_function` `${p}-driver-<slug>` (same image; `image_config.command = ["ingestion.entrypoints.sftp_pull.handler"]`; env adds `CONVEYER_FEED_ID`; role above; DLQ).
- `aws_scheduler_schedule` from `trigger.schedule` + `schedule_expression_timezone = trigger.timezone` → invoke the function with input `{}` (window defaults to ledger-fold).

Adding a feed is exactly: add `sources/<source>/<feed>/{source.yaml, contracts/, tests/}` → PR → CI green → `terraform apply` → (sftp only) `make put-secret`. No hand-built infrastructure, ever.

## 12. Testing, CI Gates, Purity Enforcement

### 12.1 Layers

| Layer | Runs against | Command |
|---|---|---|
| Unit (pure) | nothing — `core/` only | `make test-unit` |
| Golden (standing scenarios) | plan assertions (pure, §8.3) + local stack: SqlCatalog ledger (tmpdir warehouse) + moto S3/DynamoDB/EventBridge/SecretsManager + in-memory `SftpFx` | `make test-golden` |
| Integration | same local stack, factory-level (each `make_*_fx` record) | `make test-integration` |
| Smoke (post-deploy) | real dev AWS | `make smoke` — drops a fixture delivery into an incoming/ prefix, polls the ledger + event log group, asserts one `registered` row and one event |

`tests/conftest.py` provides one central fixture, `local_effects -> Effects`: the same record shape production uses, assembled from moto clients, a SqlCatalog ledger (bootstrap-created via the same `create_ledger.py` — the bootstrap script is thereby tested), an in-memory sftp dict behind `sftp_fx_for`, a controllable `now()`, and a seeded deterministic `new_delivery_id` sequence. No mocking framework anywhere (linter-banned); a test double is a local function slotted into a record. Golden tests drive **the real handlers** end-to-end with fake events.

### 12.2 Purity linter — `tools/purity_linter.py`

AST walk enforcing both purity and the §7.0 idiom. Failures list file:line:rule. The linter itself gets unit tests (fixture files that must pass/fail).

Purity rules — applied to `ingestion/core/**/*.py` and `sources/**/*.py` (effects and entrypoints exempt from these):

- **Imports** (module or any submodule): `boto3`, `botocore`, `pyiceberg`, `paramiko`, `requests`, `urllib`, `http`, `socket`, `subprocess`, `os`, `sys`, `io`, `pathlib`, `sqlite3`, `random`, `tempfile`, `threading`, `multiprocessing`, `time`.
- **Calls** (attribute-resolved best-effort): `open`, `eval`, `exec`, `__import__`, `datetime.now`, `datetime.utcnow`, `datetime.today`, `date.today`, `uuid.uuid1`, `uuid.uuid4`. (`uuid.uuid5` allowed — deterministic. "Now" is always a parameter.)
- **`raise` and `try` statements** — defects are values (§7.0 rule 4); the pure core neither throws nor catches.

Idiom rules — applied to ALL of `ingestion/**/*.py` and `sources/**/*.py` (D-17, no exemptions):

- **`class` statements** are banned unless the class is `@dataclass(frozen=True)`-decorated, a pydantic `BaseModel` subclass, or an `enum.Enum` subclass. No other base classes; no methods beyond what those forms auto-generate (pydantic validators allowed — they are the boundary-parsing mechanism).
- **Banned imports anywhere**: `toolz`, `cytoolz`, `returns`, `pyrsistent`, `funcy`, `effect`, `unittest.mock` (test doubles are records of plain functions, §7.7).

### 12.3 Unit suite highlights — `hypothesis` property tests: `canonical_content_hash` invariance under ordering/permutation + sensitivity to any name/hash change; `mint_batch_id` determinism; fold idempotence (`latest_dispositions(rows + rows) == latest_dispositions(rows)`); expectation calendar across DST transitions (America/New_York, spring + fall dates pinned).
